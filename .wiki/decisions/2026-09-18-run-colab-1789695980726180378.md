# run: The recall of absence detection fluctuates between 13/18 and 3/18 depending on how the judgment field is queried

What. Registered the `artifacts/inbox` of `colab-results-1789695980726180378.zip` as `tools/register_run.py`.
Extracted 59 files from the result ZIP into text in `reports/runs/colab-1789695980726180378/` and did not commit the ZIP binary.
The two ZIP hashes, code commits, execution environments, times, counts, and raw response statuses are in `manifest.json` in the same folder.
The source of the submitted ZIP hash is `candidate.json`.

Why. When I merged the judgment fields of the diagnostic tool into one, the discrepancies disappeared to 0/66, but the recall of absence detection dropped from 13/18 to 3/18, revealing that the "v16 6/6" of the previous round was not due to model capability but the result of a loose query.
It is the same model, same announcement, and same item. What changed is the way of querying the judgment, which contains two variables — removing the `판정` field from the schema and adding two sentences of conservative instructions (`Choose this and only this…`, `The first three values all mean 위반 없음…`) to the prompt.
Since both were introduced in the same round, it has not yet been determined which one had the effect.
v16 6→1, v18 4→2, v20 3→0, and the total number of positive judgments decreased from 370 to 66.
The submission pipeline has 0 for all three items in both rounds. Neither is "true capability" but a point created by the way of querying, which is why the recall and precision dials are on the prompt and schema side.
The next steps for the full text and C3 are owned by [absence detection diagnosis](../../reports/team-score-audit/absence-detection.md), and the records of previous rounds have also been corrected in the same document.

v20 is different. 192 out of 200 cases are `context_not_observed`, and the positive judgment is 0.
Unlike v16 and v18, which are divided into "saw it but the conditions do not match," the same prescription should not be used.

The schema modification itself was implemented as intended. However, the fact that all 66 cases of `판정=1` are `violation_found` is not a measurement — the `판정` of this round is not a value answered by the model but a value created by `parse()` as `막힌_단계 == violation_found`, so discrepancy is impossible by definition. The disappearance of the 286/370 discrepancy from the previous round means that the mechanism where the two fields refuted each other has been removed, and the accuracy of the step name is still unverified.

It is also the fifth measurement of the same `script.py` (`2ad9ea8f`). With dev 0.2202239896, the range is 0.0026 without code changes, following three instances of 0.2182 and one of 0.2208. I increased the churn observations to ten pairs and widened the cell range to 29~45 (three pairs with different code were excluded as they are not churn observations).

The notebook quality gate failed this time. `validation.json` is `quality_pass: false`, and the `macro_f1_delta` -0.0005773756926995555, which is the evidence for that judgment, is in `quality-comparison.json` in the same folder (this key does not exist in `validation.json`).
The `89a6a11` round passed by crossing the same baseline by +0.00000477, and `script.py` is the same. Another empirical case has been added to the rule that `quality_pass` is not used as evidence for adoption because the gate opens and closes in both directions based solely on churn.
