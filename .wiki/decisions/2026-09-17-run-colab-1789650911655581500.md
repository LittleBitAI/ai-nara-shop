# run: 36b6cc1 Registered the run and confirmed a 0.0025 fluctuation between runs

What. Registered `colab-results-1789650911655581500.zip` as `tools/register_run.py`. Unzipped 55 files into `reports/runs/colab-1789650911655581500/` and did not commit the ZIP binary.
The dev Macro F1 of `36b6cc1` is 0.21825534501066987, and the baseline for the same run is 0.21499821620044368.
Since `submit.zip` did not come down due to failing the quality gate, the submission ZIP hash was retrieved from the `candidate.json` noted during execution (`a5e038ea…8b669`). The result of comparing it cell-by-cell with the previously registered `654c556` run is held by [reproducibility.md](../../reports/runs/reproducibility.md).

Why. Even though the prompt, schema, model, seed, and input tokens were all identical, 25 out of 4,800 cells differed in the primary judgment of 24 items between the two runs, causing the Macro F1 to move by 0.0025; therefore, improvements smaller than that cannot be claimed by comparing runs against different baselines.
The number of output tokens differed in 33 out of 200 cases, while chunk composition, announcement order, and input token counts were all identical.
The cause is not the code or data, but the non-determinism between runs of vLLM batch inference. As this is a single pair of observations, we do not generalize 0.0025 as the magnitude of noise. The contribution of the additional v13 judgment was exactly the same for both runs (+0.0032571288102262), and the final score drop of -0.0025 came entirely from the baseline stage.

`693c695` optimization worked as intended. The number of additional call targets decreased from 200 to 107, reducing additional inference time from 330.8 seconds to 110.7 seconds (-66.5%), and the entire dev time from 896.9 seconds to 694.8 seconds (-22.5%). Since the server is using 86% of its 2-hour limit, this saving is more valuable than the score. However, server time cannot be known before actual submission because estimating it by multiplying dev seconds per case is inaccurate. This run has not been submitted yet.

Other fixes. The reason `input_sha256` differed between the two runs was not due to data differences, but because the notebook inserts the current time into the header when re-compressing as `gzip.open`. Fixed it to `mtime=0`. Also, since `submit.zip` does not come down for runs that fail the quality gate, I fixed the registrar to use the hash noted during execution. If the file exists, it prevents attaching a ZIP from a different run by comparing it with that hash.
