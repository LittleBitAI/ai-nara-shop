# 현재 계획 — 4인 팀, 1주 0.60 도전

## 바로 답할 내용

- **목표:** 9/24까지 dev Macro F1 0.60에 도전하고 실제 서버 점수는 별도로 확인한다.
  9/25~28은 일반화·실행 안정성·최종 제출 검증에 쓴다. 0.60은 현재 달성 수치가 아니다.
- **현재 실측:** 654c556의 dev F1 0.2207877113, **같은 코드의 서버 리더보드 0.2197036943**
  (2026-09-17 제출, 채점됨). 11항목 F1=0, 부재탐지 FN=31, v24/v17/v21의 FP=117/185.
  두 수는 공개 dev 200건과 비공개 1,853건이라 서로 다른 입력의 측정이다.
  693c695 이후 코드는 로컬 검사만 통과했고 새 GPU 실행·제출은 아직 없다.
  제출 이력은 [submissions.json](../reports/submissions.json)이 소유한다.
- **한 쌍의 회차에서 나온 Macro F1 차이는 신호가 아니다.** 같은 조건인데 24항목 판정이 회차마다
  4,800셀 중 29~45개 바뀌고, 그 churn의 Macro F1 영향이 같은 코드 열 쌍에서 **0.000008~0.003129**로
  400배 벌어졌다. **같은 `script.py`가 dev 0.2182를 세 번, 0.2208과 0.2202를 한 번씩 냈다**
  ([근거](../reports/runs/reproducibility.md)).
  쓸 수 있는 신호는 대상 항목의 TP/FP/FN이다 — `tools/compare_runs.py`가 낸다.
  노트북 `quality_pass`도 믿지 않는다. 같은 `script.py`인데 run4는 과거 기준선을
  0.00000477 넘겨 통과했고 run5는 0.000577 못 미쳐 떨어졌다 — churn만으로 양방향이다.
- **`36b6cc1`·`b113425` 실측:** 같은 `script.py`(`2ad9ea8f`)로 dev 0.2182553450과 0.2182114413.
  `654c556`(0.2207877113)과의 0.0025 차이는 코드 효과가 아니라 churn이 한쪽으로 쏠린 것이다 —
  run1과의 두 차이가 26%만 겹치고 방향도 7:6으로 균형이다.
  추가 호출이 200건에서 107건으로 줄어 추가 추론이 330.8초에서 110.7초로, dev 전체가
  896.9초에서 694.8초로 줄었다. 아직 제출하지 않았다.
- **부재탐지는 묻는 방식이 가른다.** 같은 모델·같은 공고인데 별도 `판정` 칸을 두면 v16·v18·v20
  재현율이 13/18, 그 칸을 없애고 보수화 지시를 넣으면 3/18이다. 제출 파이프라인은 두 회차
  모두 0/18이다. 재현율·정밀도 다이얼이 프롬프트·스키마 쪽에 있다
  ([근거](../reports/team-score-audit/absence-detection.md)).
  **두 변수가 한 회차에 같이 들어갔으므로 어느 쪽 효과인지는 아직 모른다** — 가르는 것이 C3의 첫 실험이다.
  v20만 다르다 — 200건 중 192건이 `context_not_observed`라 관측 단계에서 막힌다.
- **모델 뒤 단계 후보는 GPU를 안 쓴다.** 원응답 307건을 보관했고 `tools/replay_run.py`가
  dev 200건을 **0.6초**에 재생한다. 재생이 회차 자신의 CSV를 바이트 단위로 재현하는 것을 검사가
  지킨다. 같은 모델 출력을 쓰므로 **회차 churn이 없고 후보와 기준의 차이가 곧 효과다.**
  `--verify`는 PR #30부터 회차 커밋의 코드로 재현하는 **보관 원응답 무결성 검사**이고 HEAD를 검사하지
  않는다. HEAD 회귀는 고정 CSV 대조 검사가 지킨다. **비교 기준은 HEAD 재생 CSV다** —
  보관 회차의 `submission.csv`를 기준으로 쓰면 병합된 후처리 효과가 후보에 섞인다.
  프롬프트·스키마를 바꾸는 후보만 Colab 회차가 필요하다.
- **시간 여유가 14%뿐이다.** 그 채점 회차는 6,192초로 2시간 한도(7,200초)의 86.0%를 썼고
  남은 여유는 1,008초다. 모델 호출을 늘리는 변경 — 항목별 추가 호출, 재시도 확대,
  문서 예산 증가 — 은 전부 이 여유 안에 들어와야 한다. 서버 GPU는 L40S 1장이다.
- **첫 48시간:** C3(v16/v18)와 D1(v8)의 실제 TP 회복을 확인한다.
  계속 TP=0이면 문맥 관측→사실 추출→조건 비교→후처리에서 막힌 단계를 찾는다.
  mock·저장 응답 재사용은 새 실제 모델 성과로 세지 않는다.
- **운영:** 개발은 병렬, 운영 코드 통합·최종 제출은 순차. 한 실험에 한 가설.
  원래 서버 응답 실패 방어를 유지하며, 점수 개선을 v13 하나에 한정하지 않는다.

## 보호할 결정과 미확인 사항

최초 서버 오류는 `청크 내 62번 공고: 정상 모델 응답 재시도 실패 (ValueError)`다. 그 제출은
`5506ca0` 코드였고 채점되지 않았다. 서버 원응답을 볼 수 없어 **실제 최초 원인은 여전히 확정하지
못했다.** 뒤이은 `654c556` 제출이 채점됐다는 것이 그 원인을 규명한 것은 아니며, 24→6→1 복구가
그것을 고쳤다고 단정하지 않는다.
기존 24→6→1 복구·이진값 정규화·추가 호출 실패 시 같은 공고의 검증된 기본 판정 보존을 유지한다.
[복구 근거](../reports/t1-baseline/response-recovery.md)와
[정규화 근거](../reports/t1-baseline/response-normalization.md)를 따른다.

[693c695 최적화](../reports/t1-baseline/selective-v13.md)는 v13 기본 양성만 재검증한다.
추가 입력 토큰 약 52.5% 감소는 최신 dev 선택 기록의 로컬 토크나이저 측정이며 GPU 시간 감소율이 아니다.
전체 법령의 전항목 주입·전건 3항목 추가 호출을 근거 없이 복원하지 않는다.
프롬프트 지시는 영어, 법적 용어·원문은 한국어로 유지한다. 팀원의 낮은 점수 성공본처럼
무응답을 0으로 채워 성공 처리하지 않는다. 법령 자료는 대회 제공 스냅샷만 사용한다.

상태: **`654c556`이 2026-09-17 서버에서 채점됐다 — 리더보드 0.2197036943. 기준선 한 점이 생겼다.**
계획·점수 분석·인수인계 문서는 준비 완료. 팀원의 새 구현·GPU 실험과 `693c695` 이후 코드의
제출은 여전히 미실행이다.
실제 담당자 배정과 실행 결과가 생기면 상세 작업서와 이 요약을 함께 갱신한다.
