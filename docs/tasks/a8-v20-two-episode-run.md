새 세션에 전달할 지시: `docs/tasks/a8-v20-two-episode-run.md 를 읽고 진행하라.`

## 2. 무엇의 효과를 가르는가

회차의 목적은 제2조·별표 주입이 현재 소비자에서 v20 판정을 실제로 개선하는지 확인하고,

H4와 현재 control 사이의 분해 한계:

- v13 수리는 동일 원응답의 소비자 전후 재생으로 이미 분리했다. 이번 두 군 모두 수리된 소비자를 쓰므로 군 간 차이의 원인이 아니다. 새 응답에서 수리 효과를 따로 묻는다면 같은 응답을 수리 전후의 격리된 소비자로 CPU 재생해야 하며, 현재 OFF/ON 파일은 그 실험이 아니다.
- 출력 예약의 생성 효과는 저장 응답 재생으로 잴 수 없다. 알려면 같은 소비자·동일 visible 문서·모델·설정 아래 예약만 다른 실제 생성 대조와 반복이 필요하다. 문서 확장 효과는 예약을 고정하고 문서만 다른 별도 대조가 필요하다. 둘을 동시에 바꾸면 다시 섞인다.
- 관측 코드의 비간섭은 같은 대역 응답을 넣는 기존 CPU 계약 검사로, 기록 IO 시간의 인과 효과는 별도 계측으로 확인해야 한다. 이번 두 군 모두 관측 ON이므로 GPU 관측 OFF 대조나 오버헤드 실측은 아니다.
- 이 추가 대조들은 이번 두 회차·두 군에 넣지 않는다. 필요한 증거를 명시한 것이지 추가 회차 승인이나 구현 요청이 아니다. 따라서 이번 결과만으로 “8일 작업 전체가 점수를 얼마 올렸다”는 인과 결론은 낼 수 없다.

## 3. `gain_kind`와 점수의 교차 판정

분류 정의는 [관측 계약](../../reports/team-c/a8-v20-annex/observation-contract.json)의 `gain_kind`가 소유한다.
`v20-audit.json`의 자동 `complete`는 응답 집합 감사 완료이며 사람 의미 검토 완료가 아니다.
`semantic_review_complete=false`·`semantic_review=pending`을 승인으로 읽지 않는다.

| 대조/분류 | 자동으로 확인된 것 | 최종 셀·정답·원문과 결합한 해석 |
| --- | --- | --- |
| control → a8 `verified_quote` | 적용 가능하고 참여 인용이 `exact` 또는 `spacing_restored`, 실제 소비 동작이 `write_0`으로 전이 | 원문이 실제 참여제한 안내인지 사람 확인 후 FP→TN이면 검증된 정밀도 개선. TP→FN이면 검증된 문자열을 사용한 오판이며 손실. 최종 셀이 같으면 경로 변화만 있고 점수 효과 없음 |
| control → a8 `verified_absence` | 적용 가능·참여 인용 null 상태에서 실제 `write_1`으로 전이 | 완전관측·문서 누락/절단·실제 안내 부재·SW 사업 적용성을 확인한다. FN→TP면 검증된 부재 회복, TN→FP면 부재/적용성 오판이다. null만으로 실제 부재를 확정하지 않음 |
| control → a8 `fallback_only` | `write_* → preserve`. 기각된 인용, 적용성 붕괴, 완전관측 경로 변화 등의 원인은 `fields`와 군별 감사 행에 있음 | baseline 보존으로 최종 셀이 맞아도 A8의 검증된 개선으로 인정하지 않는다. 손실·무변화도 별도 집계하며 기각을 검증된 비위반으로 바꿔 부르지 않음 |
| control → a8 `other` | 위 전이에 해당하지 않음. 같은 소비 동작에서 사실·인용 상태만 달라지는 경우 포함 | 기전 성공에 합산하지 않는다. 최종 변화가 있으면 기존 소비/병합 경로를 추적하고 설명 전까지 미확인. 다른 항목의 점수 변화도 v20 기전으로 합치지 않음 |

각 회차마다 분모를 군별 전체 공고와 `paired_changes` 공고로 나눠 쓰고, 네 분류별로
`최종 정답 개선 / 악화 / 최종 셀 불변`의 건수와 ID를 기록한다. 두 회차 합계만 쓰지 않는다.
변경 셀 밖의 감사 행도 확인해 두 군 모두 놓친 부재·인용 실패의 분모를 남긴다.

판정은 분류 비율의 새 임계값으로 하지 않는다. 두 회차의 순이득을 설명하는 검증된
인용/부재 전이가 반복되고 §6을 만족해야 후보를 유지한다. 서로 다른 ID에서 반복되면
그 사실과 같은 기전인지의 근거를 적고, 같은 ID의 재현과 구분한다. 검증된 전이와
fallback 이득이 섞이면 각각의 기여를 분리하고, fallback 이득을 성공 근거로 포함하지 않는다.

`verified_quote`·`verified_absence`가 전혀 없고 좋아진 셀이 `fallback_only`뿐이면
“점수만 이동, 가설의 개선 기전 미확인”이다. 검증된 전이가 있어도 최종 셀이 그대로면
“기전 변화, 예측 효과 없음”이다. 사실·경로·CSV 모두 같으면 “이 두 회차에서는 주입이
아무것도 바꾸지 않았다”로 닫는다. 이는 관측·근거·보안 수리까지 무효라는 결론이 아니다.
분류 이름 자체는 문자열·소비 경로의 검증이지 법적 정확성의 보증이 아니다.

## 4. 실행 전 확인과 회차 진행

실행 조작은 [Colab 실행 안내](../../reports/team-c/a8-v20-annex/run-request.md)를 따른다.
아래는 그 단계마다 진행 여부를 판단하는 순서다. 값을 바꿔 우회하지 않는다.

1. 코드 `e6d9b98b7a40c6a6f563802445c24e2e61d9a3af`, 노트북 `9940b50b9186b87c43a746f074277dd93bea3105`를 실행 안내·CPU 원장과 대조한다. 원격에서 고정 코드를 실제 확보하고 `REPO_REF`·checkout SHA가 일치해야 한다. 로컬 객체 존재를 원격 확보 성공으로 대신하지 않는다.
2. 입력 `artifacts/a8-v20-annex/a8-v20-inputs.zip`의 30개 파일·3,264,446바이트는 [CPU 원장](../../reports/team-c/a8-v20-annex/cpu-checks.json)의 기록이다. 크기만 믿지 않고 노트북 복원 후 `inputs.json`의 모든 member SHA256을 확인한다. 노트북 전체 SHA256도 CPU 원장과 대조한다. 누락·불일치면 생성 전에 중단한다.
3. 실행 안내의 고정 모델 revision·환경 및 관측 계약을 확인한다. 두 군 공통 출력 예약·입력 예산, 스키마·샘플링·소비자·기본/SME 보관 응답을 고정한다. 이후 결과의 `contract.json`·`environment.json`과도 대조한다.
4. 사용자가 회차 1을 실행한다. 회차 선택 셀 인덱스 5에서 `EPISODE=1`, `ATTEMPT="a"`, 실행 셀 13에서 `control→a8`이다. 실제 토크나이저 예산 검사 결과 문서 동일·추가 절단 0이 아니면 생성 전 중단한다. 셀 위치의 소유자는 실행 안내다.
5. 성공·실패 모두 ZIP 셀 15로 산출물을 받는다. §5의 무결성·안정성·시간·불변식 감사 후 회차 1 판정을 기록한다. 유효하게 완료됐고 기존 중단 조건이 없으면 점수의 상승/하락만으로 다음 회차를 취소하지 않는다. 첫 회차 결과를 보고 프롬프트를 조정하지 않는다.
6. 사용자가 런타임을 삭제하고 새 A100 런타임에서 같은 핀·ZIP·ATTEMPT, `EPISODE=2`로 실행한다. 순서는 `a8→control`이다. 회차 1 미완료·시간 초과·최종 미복구·소스/입력/설정 불일치이면 진행하지 않는다. 환경 대조는 모델 적재 뒤 생성 전에 수행한다.

## 5. 결과를 받은 뒤 감사 순서

1. 원본 ZIP의 SHA256·크기·ATTEMPT·회차·획득 경로를 기록하고 원본은 덮어쓰지 않는다. A8 ZIP은 전용 파일럿 출력이다. `register_run.py`의 일반 결과/제출 ZIP 한 쌍과 같은 형식이라고 가정하지 않는다. 보관 위치·색인 갱신은 실행 기록 규약에 맞추되 이번 설계의 단일 파일 범위와 분리한다.
2. `contract.json` → `environment.json` → `budget.json` 순서로 핀·입력·모델·군·순서·설정·문서 동일성을 확인한다. 이어 `run_report.json`·`summary.json`의 완료/실패와 실제 live mode를 확인한다. mock·test double을 모델 성공으로 세지 않는다.
3. `diagnostics.jsonl`에서 루트 종료, 군/청크/물리 호출/파싱의 결속을 본다. 최초 요청의 출력 한도 실패, 재시도, fallback, 최종 미복구를 나눠 군별 집계한다. `model_call_finished`와 논리 `response`를 합쳐 성공을 두 번 세지 않는다. 실제 재시도의 메시지·스키마·예약을 최초 요청 복사본으로 대체하지 않는다. `stage_seconds`는 재시도를 포함해 상한과 비교한다.
4. 양 군 OFF/ON CSV 바이트를 먼저 대조한다. 다르면 같은 payload를 읽었는지 → 기본/SME 응답·소비자·카탈로그 초기화가 같은지 → `activate()` 복원과 군간 전역 상태 → 재생/직렬화 차이 순서로 확인한다. `consumer-comparison.json`만으로 근거 열·줄바꿈 차이를 놓치지 않는다. 출력만 정규화해 불변식을 통과시키거나 점수 개선으로 해석하지 않는다.
5. `v20-audit.json`의 contract hash와 payload 무결성·공고 집합을 확인한다. 재감사가 필요하면 고정 실행 코드와 입력이 준비된 환경에서 원본이 아닌 작업 사본에 아래 명령을 실행한다. 감사기는 실제 소비자를 호출하며 카탈로그를 초기화한다. 빈 카탈로그의 0건을 성공으로 인정하지 않는다.

```text
python -X utf8 experiments/a8_v20_audit.py --episode-dir <회차-작업사본-경로> --dev-input open/dev.jsonl
```

6. `off-comparison.json`·`on-comparison.json` 및 군별 점수에서 v20 TP/FP/FN ID와 다른 항목 전체의 변화를 확인한다. 재확인 명령은 다음과 같다. `<회차-경로>`를 실제 경로로 바꾼다. 쓰기를 요청하지 않는 명령이며 회차마다 실행한다.

```text
python -X utf8 tools/compare_runs.py --before <회차-경로>/control/off-hybrid.csv --after <회차-경로>/a8/off-hybrid.csv --truth open/dev_labels.csv --items v20 --all
```

7. §3에 따라 원응답 → 인용 상태/문서 위치 → 적용성·완전관측 → 소비 동작 → 최종 셀 → 정답을 연결한다. 참여 안내와 단순 SW 명칭을 구별하고 null·invalid·법적 비대상·자료 누락·절단을 따로 기록한다. 사람 의미 검토의 경로는 감사기 문서가 지정한 `reports/team-c/a8-v20-annex/semantic-review.jsonl`이며 검토자·근거를 남긴다. 실제 검토 전 승인 수나 검토자를 만들어 넣지 않는다.
8. 회차 2의 `repeat-<군>-<소비자>.json` 네 개에서 항목별 churn과 바뀐 ID를 읽는다. CSV 불변과 사실/인용 불변은 다르므로 두 회차 감사 행·원응답도 대조한다. 이후 회차별 결과와 기전 교차표를 함께 보고 판정한다.

이 명령들은 결과 수령 후 실행할 절차이며 이번 설계에서 GPU 산출물로 실행했다고 주장하지 않는다.
Langfuse 화면·새 서비스는 감사의 선행 조건이 아니다. 기존 JSONL·JSON·CSV로 판정한다.
단일 수출 출구의 보존/차단 확인이 필요해도 로컬 CPU 투영·기존 검사부터 사용하고 외부로 보내지 않는다.

## 6. 회차 이후 판정과 인수인계

여섯 조건의 소유자는 [착수서 §5~6](a8-v20-annex-injection.md)이고,
기전 해석은 [기존 설계 §1](../../reports/team-c/a8-v20-annex/after-a8-design.md)을 적용한다.

| 상태 | 판정 |
| --- | --- |
| 계약·불변식·완료·시간을 충족하지 못함 | 해당 비교는 무효 또는 실행 실패. 성능 기각과 구분하고 후속 회차/채택 진행 중단. 누락을 0으로 채우지 않음 |
| 두 회차 각각 TP 비감소·FP 비증가이고 TP 증가 또는 FP 감소가 반복되며 검증된 기전으로 설명됨 | 채택 후보 유지. TP 회복 주장은 두 회차 각각 TP≥2 및 control보다 증가한 경우만. FP 감소만이면 정밀도 개선으로 기록 |
| 동률·반복 개선 없음·TP/FP 조건 미달·fallback만의 이득 | A8 가설 개선 미확인으로 기각/미채택. Macro가 오르거나 관측이 풍부해져도 성공으로 바꾸지 않음 |
| 대상 밖 항목의 TP 손실 또는 FP 증가가 두 회차에 공통으로 존재 | 채택 보류. 다른 항목 손실을 숨기려고 control 사실로 바꿔 끼우지 않음 |
| 출력 한도 실패가 반복되거나 control보다 증가 | 복구 성공이어도 안정성 검토 전 채택 보류. 최종 미복구·누락은 0이어야 함 |
| 자동 감사만 완료하고 의미 검토가 미완료 | 기전 판단 미완료. 사람 검토를 기다리며 검증된 개선으로 승격하지 않음 |

채택 후보 유지도 최종 채택은 아니다. 유망할 때만 착수서 §6의 무라벨 6,000건 실제 모델
발화율·시간·독립 리뷰 작업으로 넘긴다. 그 수집은 두 회차 설계의 실행 범위 밖이고
mock·키워드 빈도로 대체하지 않는다. 전체 GPU/서버 검증과 운영 통합·제출은 별도다.

결과 인수인계는 기존 보고서 폴더의 `results.md`에 회차/핀/ZIP 식별, 군별 조건·시간·실패,
항목별 TP/FP/FN·변경 ID, 기전 교차표·의미 검토 상태, 같은 군 반복 churn, 채택/보류/기각
근거를 남기는 후속 작업으로 한다. 실제 값이 없는 칸은 미측정으로 남긴다. 현재 문서는
결과 파일·원장·작업 큐를 대신 갱신하지 않는다.

마지막 결론은 변경별로 적는다: 주입의 예측 효과, v13 근거 수리의 알려진 효과,
예약 변경의 문서 예산 효과와 미측정 생성 효과, 관측/감사의 새로 확인 가능한 사실,
수출 경계의 CPU 계약 증거. 성능 변화가 0이어도 이 구분을 유지한다.
A8이 미달이면 후속 우선순위는 기존 설계 §6을 인용하고, 이번 결과로 확인한 실패 분모만
인계한다. 새 위치·분량 탐색이나 API 사전 실험으로 회차를 늘리지 않는다.

## 7. 하지 말 것

- 새 검색기·추가 모델 호출·스키마·소비자·주입 위치/분량 변경, 추가 군·추가 탐색 회차.
- 사전 등록의 문서 동일·추가 절단 0·각 회차 TP/FP·최종 미복구 0·단계 상한 완화.
- 회차 간 Macro 차이를 전체 작업의 인과 효과나 서버 기대값으로 환산.
- 잘못된 인용의 보류 뒤 baseline 정답을 A8 개선으로 인정.
- 감사 중 모델 재호출, 미확인 자료/외부 법령 추가, 외부 전송, GPU 예약, 임의 하위 에이전트 생성.
- 원본 ZIP·보관 CSV 덮어쓰기, 다른 ATTEMPT 혼합, 일부 군/좋은 회차만 선택해 보고.
- 이 설계를 GPU 실행 승인·머지·제출·사람 승인·독립 리뷰 완료로 표시.
