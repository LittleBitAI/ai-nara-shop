# prompt-from-labels / 라벨 근거로 프롬프트를 고치면 실제로 몇 점 오르나

작업 ID / 제목: `prompt-from-labels` / Opus 5 33건의 근거 인용으로 Gemma 프롬프트를 고치고 효과를 측정
담당 역할 / 담당자: 구현자 / 미배정
상태: ready — **아직 아무것도 고치지 않았다**

## 이 티켓이 따로 있는 이유

**이 실험은 라벨링 트랙 전체의 투자 회수 측정이다.** "외부 모델로 라벨을 만들어서 얻은 근거로
프롬프트를 고쳤더니 실제 점수가 얼마나 올랐나"에 숫자가 나와야, 무라벨 20,000건에 라벨을 더
붙일지 말지가 결정된다.

그래서 **다른 개선과 섞으면 안 된다.** 후처리 변경, 문서 예산 변경, 추가 호출, v16 별도 스키마
같은 것을 같은 회차에 넣으면 개선분의 귀속이 불가능해지고, 이 실험은 답을 잃는다.
한 실험에 한 가설이라는 W5 규칙이 여기서는 티켓의 존재 이유 그 자체다.

## 목표와 가설

가설: **v8·v14·v15의 TP=0은 항목 난이도가 아니라 프롬프트가 묻는 방식 때문이다.**

근거: 같은 공고·같은 법령 스냅샷·같은 항목 정의를 받은 Opus 5가 33건에서 v8 3/3, v14 5/5,
v15 3/3을 냈다. Gemma는 6회 실행 내내 이 셋에서 TP=0이다
([실측](label-compare.md), [항목 지표](../../reports/team-score-audit/metrics.csv)).

## 읽을 문서 / 보호할 규칙 ID

[label-compare 작업서](label-compare.md)의 실측 결과, [workflow](../workflow.md) W5,
[rules](../rules.md) A1·A2·R8·R11, [items](../items.md)의 v8·v14·v15,

## 대상 항목 — 고정한다

**v8, v14, v15만 건드린다.** Opus 5가 완벽했고 Gemma가 6회 내내 0인 셋이다.

제외하는 것과 이유:
- **v16**: Opus 5도 0/3이다. 남은 근거는 이것 하나다 — **"Gemma의 별도 스키마가 이미 6/6을
  냈다"는 근거는 철회됐다.** 같은 도구의 두 번째 회차에서 v16은 1/6이었고, 6/6은 모델 실력이
  아니라 느슨하게 물어서 나온 값이었다(200건 중 145건을 위반이라 했다).
  그러므로 "다른 경로가 이미 답을 갖고 있다"고 말할 수 없다. 그래도 이 티켓에서 빼는 이유는
  부재탐지 재현율·정밀도 다이얼을 가르는 일이 C3의 별도 실험으로 잡혀 있고, 라벨 근거를
  프롬프트로 옮기는 이 티켓과 가설이 다르기 때문이다 —
  [부재탐지 진단](../../reports/team-score-audit/absence-detection.md).
- **v24**: Opus 5 FP 12, Gemma FP 43. 라벨러를 바꿔도 안 풀리는 공통 약점이라 다른 가설이 필요하다.
- **v17·v19·v21**: 오탐 문제이고 재현율은 이미 산다. 후처리 트랙 소관이다.

## 측정 설계 — 이 티켓의 핵심

### 1. replay로는 못 잰다

프롬프트를 바꾸면 모델 출력 자체가 달라진다. `tools/replay_run.py`는 보관된 원응답을 재생하므로
이 후보에는 쓸 수 없다. **Colab GPU 회차가 필요하다.** 회차 횟수는 2026-09-20부터 제한이 없으니
같은 코드로 한 번 더 돌려 churn을 함께 잰다. 다만 **서버 시간 여유는 2,919초로 여전히 유한하다**
(`57761ff` 실측 4,281초 / 한도 7,200초) — 전건 추가 호출 한 단계가 약 1,618초다.

### 2. Macro F1 한 쌍의 차이는 신호가 아니다

같은 코드가 dev Macro F1 0.2182를 세 번, 0.2208과 0.2202를 한 번씩 냈다. 회차 churn의 영향이
0.000008~0.004689로 590배 벌어진다([근거](../../reports/runs/reproducibility.md)).
**보고할 숫자는 v8·v14·v15의 TP/FP/FN이다.** `tools/compare_runs.py`가 낸다. 손으로 세지 않는다.

### 3. 오염 분리 — 이것이 실제 저울이다

근거를 **dev 33건에서 뽑았다.** 그 33건에서 점수가 오르는 것은 암기일 수 있다. 그래서 채점을
두 덩어리로 나눠 따로 낸다.

| 덩어리 | 공고 | 뜻 |
| --- | --- | --- |
| **본 33건** | 아래 ID 목록 | 근거를 뽑은 공고. 여기 개선은 암기일 수 있다 |
| **못 본 167건** | dev 나머지 전부 | **여기서 서는 개선만 일반화한 것이다** |

```
PPS-DEV-035,PPS-DEV-036,PPS-DEV-037,PPS-DEV-038,PPS-DEV-039,PPS-DEV-040,PPS-DEV-042,
PPS-DEV-045,PPS-DEV-048,PPS-DEV-049,PPS-DEV-050,PPS-DEV-051,PPS-DEV-052,PPS-DEV-053,
PPS-DEV-054,PPS-DEV-055,PPS-DEV-058,PPS-DEV-061,PPS-DEV-062,PPS-DEV-064,PPS-DEV-066,
PPS-DEV-069,PPS-DEV-072,PPS-DEV-074,PPS-DEV-076,PPS-DEV-079,PPS-DEV-081,PPS-DEV-082,
PPS-DEV-083,PPS-DEV-084,PPS-DEV-085,PPS-DEV-086,PPS-DEV-087
```

나누는 법: 정답 CSV와 예측 CSV를 같은 ID 집합으로 각각 걸러 `tools/score.py`를 두 번 돌린다.
채점기의 ID 일치 검사는 제출 계약이므로 완화하지 않는다.

**167건에서 v8·v14·v15의 TP가 0에서 오르면 — 라벨링이 값어치를 한 것이다.**
**33건에서만 오르면 — 라벨링은 이 프롬프트를 고치는 데 도움이 안 된 것이고, 그 결론도 결론이다.**

## 통과 조건

1. 대상 3항목 외 21항목의 질문·후처리·예산이 바이트 단위로 안 바뀌었다.
2. Colab 회차 1회 완주, 전 공고 정상 모델 응답, 49열·ID·인코딩 검사 통과.
3. 총시간이 기준선 대비 늘지 않았다. 늘었으면 **2,919초** 여유 안이어야 한다(`57761ff` 실측).
4. `tools/compare_runs.py`로 대상 3항목 전→후와 **비대상 21항목 회귀**를 같이 보고한다.
5. 본 33건 / 못 본 167건 채점을 **따로** 낸다.
6. ID별 예외 규칙·정답 주입이 없다(R8).

## 채택·반려

- **채택**: 못 본 167건에서 대상 항목 TP가 오르고, 비대상 항목이 회귀하지 않고, 시간이 여유 안.
- **보류**: 본 33건에서만 오른다 → 암기 의심. 프롬프트를 조건 문장으로 일반화해 다시 잰다.
- **반려**: TP는 늘었는데 FP가 폭증한다 → 대상 항목 F1과 Macro F1을 같이 본다.
  v17이 FP 42로 이미 그 실패를 하고 있으니 같은 함정을 반복하지 않는다.
