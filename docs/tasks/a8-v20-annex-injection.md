## 1. 목표와 가설

**기존 company_size 호출에 제공 지침 제2조와 별표 1 원문만 추가하면,
기존 SW 사실 추출이 개선되는지 대조군과 반복 비교한다.**

작은 조문 블록부터 주입을 검증한다는 방향은 유지한다. 새 검색기·추가 호출·금액 결정표는
만들지 않는다. 스키마·소비자·관측 게이트는 그대로 둔다. 효과가 있을지는 미측정이다.

읽는 순서: [workflow](../workflow.md), [문서 지도](../README.md),
[항목 v20](../items.md#v20), [규칙](../rules.md), [계약](../contracts.md),

`script.py`의 `COMPANY_SIZE_PROMPT` → `verify_document_requirements` → 최종 병합 경로.
조회 보고서의 토큰 표는 **글자 수 환산 추정**이며 아래 정정을 적용한다.

활용 규칙: 개발/로컬 검증 A1·A6·A9·A10, R1·R3~R5·R7~R11·R15·R18~R22.

## 2. 먼저 바로잡을 사실

| 구분 | 확인한 내용 |
| --- | --- |
| v20 | 공식 이름은 입찰참가자격 (SW), 부재탐지이며 e20은 항상 빈칸 |
| 보관 H4 재생 기준 | TP/FP/FN=1/4/4, F1=0.200. 새 control 결과와 구분 |

| company 출력 실측 | max 494 · p95 389, 200건 전부 `stop`. 운영 예약 2,048은 관측 최댓값의 4.15배다 |
| 기존 입력 | 항목표 비고에도 20억·40억·80억 구간이 있다. 숫자가 표 밖 어디에도 없다는 주장은 철회 |

별표 1에는 80억·40억뿐 아니라 **중소기업에서 중견기업이 된 지 5년 미만인 대기업의
20억원 하한**도 있다. 제2조②는 분리발주/분담이행 시 타 사업 적용 제외를 다룬다.
제3조는 VAT 포함 사업금액, 장기 유지보수 연평균 금액 등 적용 방법과 ②의 안내 의무를
다룬다. 따라서 **별표 하나가 v20 판정 규칙 전체라는 전제는 틀리다.**
이번은 제2조+별표의 추가 효과 실험이며 완전한 법적 판정기 구현이 아니다.

현재 소비자는 금액 하한을 비교하지 않는다. `software_business=yes`와 검증된 공고 인용을
확인한 뒤, `software_participation_quote`가 유효하면 0, null이고 `software_complete`를
통과하면 1을 쓴다. 조건을 충족하지 못하면 **앞 단계 판정을 보존**한다.
프롬프트는 이미 제3조②의 적용 여부·근거 안내를 찾도록 지시한다.
조문 주입은 이 사실 관측에만 영향을 줄 수 있고 새 금액 판정 경로를 만들지 않는다.

## 4. 주입 계약과 CPU 사전 검증

1. `law_index.article(법령명, "제2조")`와 `law_index.annex(법령명, 1)`을 직접 사용한다.
   법령명은 `중소 소프트웨어사업자의 사업 참여 지원에 관한 지침`이다. None/빈 조각이면
   실행을 중단한다. 두 조각은 제공 원문의 부분문자열이어야 하며 20억원 행도 보존한다.
2. 기존 `COMPANY_SIZE_PROMPT` 끝에 구분된 법령 참조 블록만 붙인다. 지시는 영어,
   원문은 한국어다. 법령은 공고 인용 근거가 아니며 null을 법적 추론으로 채우지 않는다.
   기존 프롬프트·스키마·소비자 hash와 차이를 남기고 종료/예외 시 임시 교체를 복원한다.
3. **고정 모델 revision의 실제 토크나이저와 제출 chat template**로 두 군의 전체 메시지를
   센다. company_size와 똑같이 `조항호내용`을 제외한 meta, 동일 products·문서 선택·
   max_chars·입력 예산·출력 예약량을 사용한다. CPU로 가능하나 토크나이저가 없으면
   Colab에서 모델 생성 호출 전에 검사한다. mock/글자 환산으로 통과 처리하지 않는다.
3-1. **출력 예약을 두 군 모두 1,024로 줄여 프롬프트 예산을 15,296으로 올린다**(2026-09-21 사용자 결정).
   블록 1,046토큰까지 추가 축소 0/200이고 관측 최대 출력 494의 2.07배가 남는다.
   이것은 아래 4의 조건을 **낮추는 것이 아니라 만족시키는 방법**이다 — 문서 손실 0, 법령 원문 변형 0,
   군 간 차이는 여전히 프롬프트 하나다. 파일럿 한정이며 운영 채택은 단계별 예약이 필요해 별건이다.
   **실측 완료(CPU, 생성 0회): 블록 586토큰, 200건 전부 같은 비용, 추가 축소 0/200,
   최대 공고 `PPS-DEV-189` 후보 14,868 — 여유 428.** `token_count_kind=actual`이며
   같은 측정을 운영 예산으로 하면 13건이 깎인다. 근거는 `reports/team-c/a8-v20-annex/budget-cpu.json`.
4. 공고별 control/후보의 토큰 수, max_chars, 실제 visible 문서 hash, 완전관측 게이트,
   축소 여부를 `budget.json`에 남긴다. **추가 축소 0/200, 두 군 공고 본문 동일**이 조건이다.
   control에 이미 있던 절단은 따로 보고한다. 공통 예산을 더 줄여 억지로 맞추지 않는다.
   하나라도 추가 절단되면 현재 설계의 GPU 실행을 중단한다.
5. 같은 H4 원응답을 후보 OFF/ON으로 재생해 **24항목 전체 CSV 바이트 동일**을 확인한다.
   소비 경로를 바꾸지 않으므로 v20도 같아야 한다. 이것은 배선/회귀 검사이며 주입 효과가 아니다.
   생성 메시지에만 참조 블록 차이가 있고 라벨·ID별 규칙이 새지 않는지 검사한다.
   **2026-09-21 라운드 2 정정:** 재생은 프롬프트를 읽지 않으므로 바이트 동일은 **같을 수밖에 없다** —
   배선 검사로 쓰지 않고 `activate()`가 재생 경로를 건드리지 않았다는 정적 불변으로만 읽는다.
   법령 문자열이 항목으로 새는지는 **결정적 소비자 스윕**이 잡는다(공고 200건 × 인용 필드 7개,
   그리고 분류·역할·인용을 함께 바꾼 결합 경로). 측정 결과는 보고서가 소유한다.

## 5. GPU 전에 고정할 판단 기준

초판의 **TP≥3**은 이번 변경 범위와 맞지 않는다. H4 FN 131·134·24는 실제 제안요청서
탈락과 완전관측 false로 막힌다. 같은 baseline과 관측 게이트를 유지하면 company 주입으로
이 셋을 양성으로 바꿀 수 없다. 남은 FN 132는 SW 적용 대상 추출에서 막혔다.
따라서 고정 H4 혼합 비교에서 도달 가능한 TP 상한은 **2**다. 이 분석을 구현 기준에서
다시 확인하고, 원자료가 다르면 GPU 전에 이유와 기준을 기록한다. 게이트를 풀지 않는다.

| 조건 | 사전 등록 기준 |
| --- | --- |
| 입력 | §4 실제 토크나이저 검사 통과, 공고 본문 동일, 기존 절단 상태 보존 |
| 탐색 성공 | 두 회차 각각 v20 TP가 control 이상이고 FP가 control 이하이며, TP 증가 또는 FP 감소가 반복됨 |
| TP 회복 주장 | 위 조건과 별개로 두 회차 모두 TP≥2이며 control보다 증가해야 함. FP 감소만이면 정밀도 개선으로 기록 |
| 대상 밖 | 23항목 TP/FP/FN·변경 셀을 모두 기록. 두 회차 공통 TP 손실/FP 증가가 있는 항목이면 채택 보류 |
| 실행 안정성 | 최종 미복구·누락 0. 출력 한도 실패·재시도·fallback을 최초 시도부터 집계하고 복구 성공과 구분 |
| 시간 | 각 후보 company 단계 ≤339.178초/200건. control 시간도 함께 기록 |

시간 상한은 `246.985 + 820 / ((1853/200)×0.96)`이다.
조건부 서버 시간은 `6380 + (후보 단계 초 - 246.985)×8.8944`로 보고한다.
이는 과거 환경 기준 추정이며 서버 보장이 아니다. 실제 단계 시간에는 재시도도 포함한다.
출력 한도 실패가 반복되거나 control보다 늘면 복구됐어도 안정성 검토 전 채택을 보류한다.

과거 A5 control 두 회차 Macro 차이 0.015666은 **관측 한 쌍의 차이**이지 ±허용선이 아니다.
새 코드의 흔들림은 새 두 회차로 측정한다. Macro와 24항목 지표를 모두 보고하되,
Macro 상승 하나만으로 채택하지 않는다. 위 조건 통과도 운영 채택을 자동 승인하지 않는다.

## 6. 실행 순서와 기록

1. 후보와 CPU 검사를 구현하고 §4를 통과한다. 재사용한 실행기의 기존 검사도 실행한다.
   독립 리뷰는 사용자가 마련한 **다른 세션**에서 받는다. 특정 모델을 강제하거나
   임의로 하위 에이전트를 만들지 않는다. 수정한 본인 검사는 독립 리뷰로 세지 않는다.
2. 코드·노트북·입력·모델·설정·프롬프트 hash를 고정한다. 같은 ZIP으로
   회차1 control→후보 각 200건, 새 런타임 회차2 후보→control 각 200건을 실행한다.
   `RUN_DIAGNOSTIC=True`. 기존 baseline/SME 원응답은 두 군·두 회차에 동일하게 사용한다.
3. 각 군의 새 company 원응답을 기존 소비자에 **그대로 전부** 넣어 혼합 CSV를 만든다.
   다른 항목의 후보 사실을 control 사실로 교체해 회귀를 감추지 않는다.
   24항목 지표·v20 TP/FP/FN ID·원문·게이트별 변화와 두 회차 churn을 기록한다.
   `tools/score.py`, `tools/compare_runs.py`를 재사용한다. CPU 테스트로 TP 성과를 보장하지 않는다.
