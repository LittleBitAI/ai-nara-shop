# 무라벨 40건 라벨링 — 표본 설계가 실패했다

2026-09-22. Opus 5 로 `open/train_unlabeled.jsonl` 에서 40건을 라벨링했다.
목적은 astra 가 낸 후보 넷(v3·v4·v13·v17)을 dev 밖에서 검증하는 것이었고,
그 목적은 달성하지 못했다. 라벨 자체는 40건 전부 받았다.

산출물은 [opus5-unlabeled40.jsonl](opus5-unlabeled40.jsonl)이다.
41행 40공고이며 `PPS-D-017733` 한 건이 할당량 실패 후 재시도로 중복이다. 뒤엣것을 쓴다.

## 규칙 판단

| 칸 | 값 |
| --- | --- |
| 단계 | 개발 · 라벨 생성 |
| 활용 A-ID | A2 제공 무라벨 자가 라벨링 전면 허용. A3 라벨 생성 단계의 외부 LLM 허용 |
| 지킬 R-ID | R6 입력은 제공 자료만, 웹 검색 결합 금지. R9 평가 입력 라벨링으로 자산·규칙 갱신 없음. R15 명령·모델·프롬프트 해시·원응답 보존 |
| 명령 | `claude -p --model claude-opus-5 --allowedTools Read,Glob,Grep --disallowedTools WebSearch,WebFetch` |

번들은 저장소 밖에 만들었다. `open/dev_labels.csv` 와 과거 오답 분석이 같은 트리에 있으면
CLI 가 문맥을 찾다가 정답에 닿기 때문이고, 그것이 `tools/label_bundle.py` 의 존재 이유다.

## 무엇을 노렸나

astra 의 [판정](../../artifacts/review/quoted-fp-result.md)이 후보 넷을 냈고 넷 다
확인된 정탐 손실이 0/8·0/6·0/3·0/5 였다. 다만 그 수치는 수동 대조값이고 구현 후 재생
실측이 아니다. 그리고 dev 200건으로 검증하면 그것이 곧 dev 를 외우는 것이다 —
[A4 서버 결과](../submission-a4-server-result.md)가 그렇게 졌다.

그래서 무라벨에서 그 넷이 걸리는 공고를 골라 라벨을 붙이려 했다.

## 왜 실패했나

층을 항목의 텍스트 전제로 짰다. 본문에 `중소기업…제한` 이 있으면 v17 층에 넣는 식이다.

| 층 | 모집단 | 표본 | 그 층의 대상 항목 양성 |
| --- | ---: | ---: | ---: |
| v3 | 2,502 | 12 | 2 |
| v4 | 977 | 8 | 0 |
| v17 | 1,245 | 8 | 0 |
| v13 (등록 계약방법=수의 + 소기업 문구) | 8,029 | 8 | 0 |
| 표식 없음 | 16,161 | 4 | 0 |

그 전제는 "이 항목이 발화할 조건" 이지 "이 항목이 위반일 조건" 이 아니다.
대부분의 공고는 그 문구를 갖고도 적법하다. dev 200건에서 v17 양성이 6건, v4 가 6건으로
비율이 3% 다. 8건을 뽑으면 기대 양성이 0.24건이니 0이 나오는 것이 정상이고,
정규식이 그 비율을 거의 못 높였다.

`v13` 을 본문 `소기업|소상공인` 으로 고르려다 20,000건 중 16,671건이 걸려서 버렸다 —
소상공인 확인서가 거의 모든 공고의 제출서류 목록에 있다. 등록 `계약방법` 으로 좁혔지만
그래도 양성은 0이었다.

지난 `--cover 3` 이 정답 CSV 로 "항목마다 양성 N건" 을 보장했던 이유가 이것이다.
무라벨에는 정답이 없어 그 장치를 못 쓰는데, 그 공백을 정규식으로 메울 수 있다고
가정했고 그 가정을 재기 전에 2시간을 썼다.

## 그래도 건진 것

| | 건수 |
| --- | ---: |
| 전 항목 음성 공고 | 20 |
| v24 양성 | 9 |
| v2 양성 | 8 |
| v18 양성 | 4 |
| v3 양성 | 3 |
| v10 양성 | 3 |

전 항목 음성 20건이 오탐 측정의 분모다. 우리가 그 공고에서 1을 쓰면 그것이 곧 오탐이다.
A4 와 [227631f](../submission-227631f-server-result.md)를 둘 다 무너뜨린 것이 오탐이었고,
그것을 dev 밖에서 세는 수단이 지금까지 없었다.

이 라벨은 정답이 아니라 두 번째 의견이다. Opus 5 를 같은 방식으로 dev 33건에 붙여 재니
Macro 0.6205 로 우리 파이프라인의 현재 0.6103 과 비슷한 수준이다
([label-compare](../../docs/tasks/label-compare.md)). 라벨이 갈리는 자리는 원문을 봐야 한다.

## 다음에 제대로 하는 법

무라벨에서 특정 항목의 양성을 뽑으려면 텍스트 전제가 아니라
우리 파이프라인이 그 항목을 1로 예측한 공고를 골라야 한다. 그러면 외부 라벨이
그 예측의 정오를 직접 판정하고 오탐이 바로 세어진다.

그러려면 무라벨에 회차를 한 번 돌려 예측을 얻어야 한다. dev 200건 회차가 934초였으니
무라벨 2,000건이면 약 2.6시간이고, 서버 한도와 무관한 준비 회차다.

라벨링 자체는 건당 106~179초였다. 40건에 4,013초 + 1,508초가 들었고 할당량으로 한 번
끊겼다. 같은 명령을 다시 치면 끝난 ID 를 건너뛴다.
