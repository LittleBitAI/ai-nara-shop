# API 호스팅 Gemma는 서버 vLLM Gemma의 점수 대리가 되지 못한다

측정일 2026-09-18. 입력은 공개 dev 앞 100건, 코드는 `9a0563e`~`c613bbb` 시점의 HEAD다.
실행은 `tools/api_run.py`(mode=`api`)이고 대회 R4 정상 호출도 서버 점수도 아니다.

## 한 줄

같은 프롬프트·같은 스키마·같은 후처리인데 Macro F1이 0.4216에서 0.2597로 0.1619 떨어졌고
24항목 판정 2,400셀 중 114셀이 바뀌었다. 이 저장소가 실측한 회차 간 churn은 Macro F1
0.000008~0.003129이므로, 이 차이는 그 범위의 50배 이상이고 무작위 흔들림이 아니다.

## 무엇을 통제했나

| 통제한 것 | 확인 방법 |
| --- | --- |
| 입력 공고 | 같은 dev 100건. 채점·대조 도구가 ID 집합 일치를 강제한다 |
| 시스템 프롬프트 | `system_prompt_sha256` = `56f73f0b…` 양쪽 동일 |
| 출력 스키마 | `schema_sha256` = `1f859041…` 양쪽 동일 |
| 후처리 | 기준선도 HEAD 코드로 재생(`tools/replay_run.py`). 보관 CSV를 기준으로 쓰지 않았다 |
| 바뀐 것 | 모델 호스팅 하나 — L40S의 vLLM+int8+xgrammar 대 Google AI Studio API |

기준선은 보관 회차 `colab-1789655036303880754`(코드 `b1134257d`)의 원응답을 HEAD 코드로
재생한 CSV에서 같은 100건을 잘라 썼다.

## 어느 항목이 갈렸나

API 쪽이 훨씬 보수적이다. v24의 FP를 22에서 2로 지웠지만 TP 4개도 같이 잃어 F1은 0이 됐다.
v17도 같은 모양이다. 정밀도를 얻고 재현율을 더 크게 잃는 교환이며, Macro F1에서는 손해다.

## 복구 경로가 원인이 아니다

폭주로 분할 재시도를 거친 공고는 8건이고 재시도에서는 프롬프트가 달라지므로 비교 대상이
아니다. 그러나 그 8건은 바뀐 셀 114개 중 14개만 설명한다. 나머지 100개는 한 번에
정상 응답한 92건에서 나왔다. 차이는 복구 방식이 아니라 모델 판정 자체에 있다.

## 폭주 — 서버에는 없는 실패

API의 `responseJsonSchema`는 키 구성만 지키고 `maxLength`를 강제하지 않는다. 근거 문자열
안에서 같은 구절을 반복하다 출력 2,048토큰을 다 써 JSON이 닫히지 않는 일이 107회 중 7회
(6.5%) 났다. 입력 3,897~11,381토큰으로 공고 길이와 무관했고 끊긴 항목도 v5·v17·v23으로
제각각이었다. xgrammar는 토큰마다 문법을 강제하므로 서버 회차에는 이 실패가 없다.
복구는 제출 코드의 6항목 분할(`VLLMRunner.retry_chat`)로 7/7 성공했다.

## 그래서 무엇에 쓰고 무엇에 쓰지 않나

쓰지 않는다. 서버 점수 추정, 후보 채택·반려 판정, Colab 회차 대체. 절대 점수가 옮겨가지
않는다는 것이 이 측정의 결론이다.

쓴다. 프롬프트·스키마 후보를 몇 건으로 빠르게 보기, 모델이 어떤 문맥을 관측하는지 확인,
표본 쌓기, 그리고 후처리 후보용 재생 corpus 확보(원응답이 `replay_run.py`로 바이트 단위
재생되는 것을 확인했다). 어느 경우든 결과를 항목별 TP/FP/FN으로 읽고 절대 점수로 읽지 않는다.

## 아직 모르는 것

- 이 차이가 모델 리비전·양자화 때문인지 제약 디코딩 차이 때문인지 가르지 못했다.
  두 변수가 한 회차에 같이 들어갔다. 가르려면 같은 호스팅에서 디코딩만 바꾼 회차가 필요하다.
- dev 뒤 100건은 돌리지 않았다. 이 표는 앞 100건의 것이다.
- 기준선 Macro F1 0.4216은 dev 200건의 0.2182와 다른 입력의 수다. 100건 부분집합이라
  항목별 양성 수가 적어 Macro F1이 크게 흔들린다. 두 수를 비교하지 않는다.
