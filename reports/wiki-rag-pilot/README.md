## 공통 문서 예산 — 이번 설계에서 가장 비싼 대목

세 군이 **같은 공고 본문**을 봐야 하므로, 세 군이 모두 토큰 예산을 통과하는 공통
`max_chars`를 추론 전에 고정한다. 그 값은 블록이 가장 큰 `wiki` 군이 정한다.
따라서 `control`도 통상 A보다 본문을 더 잃는다. 이것은 숨기지 않고 공고별로 기록한다 —
`budget.json`의 `usual_control_max_chars`, `additional_truncation_chars`, 본문 hash 두 개.

[budget-estimate.json](budget-estimate.json)의 **계획 추정치**(실제 토크나이저 측정이 아니다.
H4 회차의 기록된 `prompt_tokens`로 낸 산술이다):

- dev 200건 중 **100건**이 통상 A보다 본문을 잃는다.
- 공통 `max_chars` 중앙값 15,970.5, 최소 **8,845**. 추가 절단 합계 416,185자.
- 블록 크기: `raw` 4,505자, `wiki` 7,199자.

그래서 **개선이 없어도 그것이 페이지의 실패라고 단정할 수 없고**, 개선이 있어도 절단 손실을
감수한 값이다. 회차 결과를 읽을 때 `budget.json`을 먼저 본다.
최소 예산에서도 토큰을 넘으면 추론을 한 번도 하지 않고 멈춘다.

## 확인한 것과 확인하지 못한 것

확인한 것(CPU):

- 12개 span의 오프셋이 원문을 그대로 재현하고, 앵커로 숫자 없이 재유도된다.
- 원본 SHA256·오프셋·인용문 훼손, 페이지의 span 누락은 실행 전에 거부된다.
- 세 군의 system 메시지·출력 스키마가 동일하고 user 메시지는 `control + 블록`과 바이트 동일.
- 세 군의 공고 본문 hash가 같다. 통상 A와의 차이는 공고별로 남는다.
- H4 보관 응답 재생이 세 군 모두 기존 HEAD 재생 CSV와 **바이트 동일**.
- 관측된 v20 변화 1건이 verifier와 최종 CSV까지 이어지고 나머지 199건은 그대로다.
- 법령 인용을 공고 인용 자리에 넣으면 기존 검증이 거부한다.
- 모의 두 회차의 순서 역전·비교·24항목 지표·실패/시간초과 보존, 회차 2의 입력·계약·
  GPU 환경·문서 예산 대조.

확인하지 못한 것:

- **실제 GPU 회차 0회.** 후보의 F1·단계 시간·프롬프트 토큰·파싱 실패율 전부 미측정이다.
- 실제 Gemma 토크나이저 측정 0회. 위 예산 수치는 추정이다.
- 무라벨 발화율, 전체 파이프라인 GPU, 서버 점수 전부 미측정.
- 독립 리뷰 미실행. 자체 검사 통과는 독립 리뷰가 아니다.
- 자산의 사람 검토 미실행. `approved`나 검토자 이름을 만들지 않았다.
- 구현 전 실패 테스트를 먼저 쓰지 않았다. 대신 세 가지 변이를 넣어 검사가 실제로
  잡는지 확인했다(cpu-checks.json의 mutation check).

## 시간 경계

기존 A5 정의를 그대로 쓴다. `(1853/200)×0.96 = 8.8944`, 단계 상한 **339.177840초/200건**,
조건부 서버 총초 `6380 + (단계초 − 246.985) × 8.8944`. 군마다 따로 재고 초과하면 실패로 남긴다.
세 군 실험 총시간은 제출 한 군의 시간이 아니다. 블록이 프롬프트 토큰을 늘리므로
단계 시간이 늘어날 수 있다 — 실측 전에는 모른다.
