# 9/25 서버 전이 진단과 0.72 실행안

판정: 무라벨 20,000건을 쓸 시점이다. 우선 용도는 새 검증 라벨과 오류 유형 확보다.
전량 자동 라벨링이나 BM25 추가 자체를 점수 상승으로 간주하지 않는다.
이 문서는 조사 결과와 제안이며 GPU·유료 라벨링·서버 제출을 실행한 기록이 아니다.

## 재현한 사실

`python -X utf8 reports/server-gap-20260925/audit.py`를 저장소 루트에서 실행했다.
기존 `tools/replay_run.py`·`tools/score.py`를 재사용했다. 결과는 [audit.json](audit.json).
현재 `script.py` SHA-256과 제출 장부의 `4a15529` SHA-256 일치도 검사했다.

예상 0.61~0.65는 지난 변경의 전이율 0.55~0.82가 이번에도 유지된다는 가정이었다.
그 가정이 틀렸다. 실제 점수는 상승했고, 기대한 상승량이 전이되지 않았다.
0.323도 다음 변경의 예측 계수로 쓰지 않는다.
이 제출 코드의 동일 ZIP GPU dev 회차는 장부에 없으므로 재생 0.7704와 GPU 측정을 섞지 않는다.

## 원인: 어디까지 확인됐나

확정된 평가 설계 문제는 dev 200건으로 규칙·임계를 고르고 같은 200건으로 성과를 재는 것이다.
항목당 양성은 5~8건이다. 한두 셀의 성공이 항목 F1을 크게 바꾼다.
다섯 원응답은 같은 공고의 반복 측정이며 독립된 1,000건 검증이 아니다.
#146의 여러 통과 임계 조정은 실행 안정성을 보지만 새 문서 일반화를 검증하지 않는다.
반복적인 검증셋 선택이 낙관적 평가를 만드는 원리는
[scikit-learn 검증 문서](https://scikit-learn.org/stable/modules/cross_validation.html)와 일치한다.
이미 사용한 200건을 지금 나눠도 과거 선택의 누출을 없애지는 못한다.

전수 입력 집계:

| 특징 | dev 200 | 무라벨 20,000 |
| --- | ---: | ---: |
| 수의계약 | 35 (17.50%) | 8,961 (44.805%) |
| 제한경쟁 | 135 (67.50%) | 8,473 (42.365%) |
| 물품 | 78 (39.00%) | 7,529 (37.645%) |
| 완전관측=false | 10 (5.00%) | 853 (4.265%) |
| 기본 16,000자 문맥의 잘림 또는 누락 표시 | 90 (45.00%) | 8,950 (44.75%) |

계약방법별 dev TP/FP/FN을 무라벨 비중으로 재가중하면 제출 코드의 다섯 재생은
0.7663·0.7708·0.7663·0.7956·0.7648이다. 원래 평균 0.7704와 거의 같다.
따라서 확인한 계약방법 구성비 차이만으로 큰 간격을 설명할 수 없다.
이 계산은 계약방법 안의 오류율이 같다는 민감도 분석이다. dev에 없는 지명경쟁 83건은
계산 대상 밖이며, 무라벨이 서버와 같은 분포라는 증거도 없다. 서버 예측값으로 쓰지 않는다.

가장 유력한 가설은 dev 선택 편향과 계약유형 안의 문구·품목·양성 빈도 차이다.
서버 항목별 TP/FP/FN과 원응답이 없으므로 어느 규칙이 얼마를 잃었는지는 미확정이다.
묶음 전체가 이겼으므로 증거 없이 규칙을 되돌리지 않는다.
L40S 서버와 A100 로컬의 실행 차이·출력 변동도 남아 있지만 이번 간격의 원인으로 정량 확인하지 못했다.
dev 라벨 노이즈는 `docs/qna.md`의 확인 범위만 인정하며 전체 간격의 설명으로 확대하지 않는다.

## dev와 서버를 맞춘다는 목표

양쪽은 같은 24항목 Macro F1 정의를 쓴다. 기존 채점기는 ID 대응 후 항목별 양성 F1을 평균한다.
동일 숫자를 강제로 만드는 보정식은 성능 향상이 아니다. 앞으로 맞출 것은 후보의 개선 방향과
기대 증가량의 신뢰성이다. 평가 집합이 다르고 서버 라벨을 모르므로 숫자 일치는 보장할 수 없다.

F1은 양성 비율에도 의존한다. 민감도 t, 오탐률 f, 양성 비율 p이면
`F1 = 2*p*t / (p*(1+t) + (1-p)*f)`다. 같은 판별 능력도 p가 달라지면 F1이 달라진다.
양성만 모은 새 검증셋이나 후보가 지운 셀만 라벨한 집합의 F1은 서버 대리값이 아니다.

## 무라벨 사용안

1. 새 라벨 예산의 첫 단위를 600공고로 제안한다. 400건은 20,000건에서 무작위 추출해 봉인 검증용으로,
   200건은 약한 항목·후보 간 불일치·첨부 꼬리의 근거를 찾는 진단용으로 쓴다.
   기존에 확인한 라벨과 중복 문서군은 분리하고 추출 이력·확률·출처를 남긴다.
   희귀 양성이 부족하면 해당 항목의 결론을 보류하거나 진단 표본을 늘린다. 600건이 충분하다고 보장하지 않는다.
2. 외부 라벨 초안은 항목별 dev 보정과 원문 확인을 거친다. 기존 v4·v13 및 C·D 사실 라벨러의
   재현율 실패를 무시하지 않는다. 라벨러 합의만으로 정답으로 승격하지 않는다.
   부재탐지는 문서 관측 범위를 함께 확인한다. 미확인은 0으로 채우지 않는다.
3. 진단 200건으로 후보를 개발하고 봉인 400건은 후보를 고정한 뒤 평가한다.
   반복적으로 보고 튜닝했다면 그 집합도 개발셋으로 바뀌었다고 기록한다.
   전체 항목 라벨이 완성되지 않으면 24항목 Macro를 만들지 않고 검증된 항목만 보고한다.
4. 기존 무라벨 원응답 약 5,500건은 후처리 발동·변경 셀 표집에 재사용한다.
   오래된 프롬프트의 응답으로 새 프롬프트 효과를 평가하지 않는다.
   전체 20,000건 GPU 실행은 한 장에서 단순 환산 약 20시간 규모이므로 먼저 작은 공통 표본에서
   라벨 품질과 개선 기전을 확인한다. 이 시간은 기존 200건 속도 외삽이며 실측·라벨링 시간은 아니다.

## BM25와 다른 변경의 우선순위

BM25는 질의와 문서의 단어 일치를 이용하는 검색 순위 기법이다
([원리](https://nlp.stanford.edu/IR-book/html/htmledition/okapi-bm25-a-non-binary-model-1.html)).
이 프로젝트의 우선 실험은 법령 추가가 아니라 공고 내부의 근거 회수다.
`build_context()`는 문서 종류 순서대로 앞부분을 취한다. 입력에 존재하지만 잘린 입찰조건·모델명·
첨부 표가 있는지 먼저 오류별로 확인한다. 실제 토큰 예산 축소는 16,000자 감사보다 더 잘릴 수 있다.

| 후보 | 첫 측정 | 채택 판단 |
| --- | --- | --- |
| 문서 내부 문단 선택 | 기존 문맥 밖에 있는 정답 근거를 키워드 창 또는 BM25가 회수하는지 | 같은 토큰 상한·같은 호출 수로 GPU 두 회차, 새 라벨 표본에서도 TP/FP/FN 개선 |
| 검증된 사례 검색 | 새 진단 사례에서 같은 법적 경계의 양성·음성 예시를 고정해 1~2쌍 제공 | 현재 dev를 예시로 쓰고 자기 자신을 맞힌 점수 제외. 봉인 표본에서 개선 |
| 경쟁제품 사실 판정 정밀화 | v10·v11·v13 등의 품목 코드·행의 조건·자격 주체 오류 분해 | 제공 CSV 정확 코드 조회 우선. 코드가 없을 때만 검색 후보. 기존 N3의 효과를 먼저 확인 |
| 선택적 재검증 | 남은 오류가 분명한 공고 조건과 기존 추가 호출 대체 가능성 | 시간 여유 내에서 오류 회복, 실패 시 기본 판단 보존 |

BM25보다 키워드 주변 원문 창만으로 충분하면 그 구현을 쓴다. 검색된 문단에 요건이 없다는 이유로
전체 문서의 부재를 선언하지 않는다. 목록 머리말·표 헤더·예외 조항·문서 출처를 같이 보존한다.
기존 법령 추가 실패(#82·#90), v2 프롬프트 실패(#92), thinking 실패를 근거 없이 재개하지 않는다.
확정 사실 추출 후 정해진 법적 조건을 적용하는 변경과 공고 근거 회수가 우선이다.

## 0.72를 향한 제출 일정

필요 증가는 `0.72 - 0.5930337159 = 0.1269662841`이며 24항목 F1 증가의 합은 3.04719여야 한다.
8항목에서만 벌면 항목당 평균 +0.38090이 필요하다. 이는 목표 규모의 산술이며 예측이 아니다.
그래서 한두 임계 미세 조정보다 여러 항목에 걸친 사실·문서 해석 오류를 고쳐야 한다.
다섯 재생의 약한 축은 v10 0.465, v18 0.490, v24 0.525, v2 0.530, v9 0.587,
v11 0.618, v16 0.642, v13 0.686이다. 이것은 개발 우선순위이며 서버 항목 순위는 모른다.

| 날짜 | 실행안 | 제출 후보의 조건 |
| --- | --- | --- |
| 9/25 밤 | 새 표본·라벨 확인 분담, 현재 오답의 근거가 문맥 밖인지 감사, 최신 코드 GPU 기준선 확보 | CPU 조사 완료. 라벨링·GPU는 별도 실행 필요 |
| 9/26 | 동일 호출·토큰 예산에서 문서 선택 한 가설 실행, 경쟁제품 오류 진단 병행 | 발동 확인 → 두 GPU 회차 → 대상 항목 개선·대상 밖 회귀 확인 |
| 9/27 | 검증된 사례 또는 사실 판정 후보 중 실측이 좋은 하나를 결합 | 새 라벨의 진단 표본에서 효과 확인, 최종 후보 봉인 평가 |
| 9/28 | 이긴 변경만 통합, 원응답 반복 재생·동일 ZIP GPU 두 회차·실행시간 검증 | 총시간 목표 6,800초 이하로 여유 확보. 7,200초는 공식 한도 |
| 9/29 오전 | 마지막 검증된 후보 또는 최고 검증 버전 제출 | 서버 실행이 마감 전 완료되어야 하는지 확인하고 최소 2시간+여유 선행 |

이 일정은 매일 상승을 보장하지 않는다. 일일 슬롯은 준비된 최선 후보에 쓴다.
동일 코드 재제출은 변동을 보는 값이 있지만, 이번 마감에서는 유망 후보가 없을 때의 선택으로 둔다.
추가 시간은 현재 844초뿐이다. 전건 N1·N3 추가 호출을 그대로 얹기보다 기존 호출 대체·짧은 문맥·
선택 조건을 측정한다. 별도 학습 모델·가중치·평가 공고 간 통계는 사용하지 않는다.

확인 완료: CPU 전수 20,200건 집계, 다섯 원응답의 두 코드 재생, SHA 일치, 기존 F1 계산 검산.
미실행: 새 라벨 600건, BM25 후보 구현·GPU 효과, 새 서버 제출. 0.72는 목표이며 실측 전망치는 아직 없다.
