# A3 H2 — 본문의 요건과 등록값을 분리한다

**후속:** [회차 3](run3-facts.md)은 v10 0/1/7, v18 1/2/6, v20 0/0/5로 세 TP 조건에 실패했다.
다음은 [H3 조항 관측](h3-observed-clauses.md)이다. 아래 미측정 표기는 H2 착수 당시 기록이다.

2026-09-20. 시작점 `6738328`. **실제 모델 미실행·성능 미채택**이다.
[회차 2](run2-facts.md)의 H1 실패를 입력으로 삼았다. 두 회차 모두 v10 0/0/7,
v18 0/1/7, v20 0/0/5이며, 같은 ZIP churn은 16셀·Macro 0.005077299914다.

## 가설과 구현

등록된 법적 제한값을 제외한 본문에서 적용 대상과 요건의 존재/부재를 각각 추출한다.
기존 company_size 호출 하나를 확장한다. 구성요소별 효과를 분리한 실험은 아니며,
추가 전건 호출·외부 API·외부 법령·새 의존성은 없다.

- company_size 입력에서만 `meta.조항호내용`을 제외한다. 원본 입력과 24항목 첫 호출은 그대로다.
  메타의 구매 대상·금액은 참고하되 본문 요건의 인용을 대신하지 못한다.
- `direct_production`은 직접생산 요건의 존재/부재/비해당/불명을 구분한다.
  기존 scope가 경쟁제품이고 본문 적용 대상 인용·완전 관측을 확인한 부재만 v10으로 연결한다.
- v18은 기존 qualification과 결정표를 그대로 쓴다. 추가 소비 규칙을 만들지 않는다.
  서류 목록·법령 인용은 자격 제한이 아니고, 명시적인 규모 제한 표제는 제한이다.
  038·043·044와 039의 구분은 새 원응답으로 확인해야 하며 CPU 검사로 성공을 주장하지 않는다.
- SW는 구매 대상인 소프트웨어 사업과 참여제한 명시를 분리한다. 관련 없는 업무 수행에
  쓰는 SW 도구나 장비 설명 속 언급만으로 사업을 확정하지 않는다. 본문 인용으로 사업을
  확인하고, 공고문/RFP가 온전히 보인 상태의 명시 부재만 v20으로 연결한다.
  SW 금액 구간별 모든 위반을 구현한 것은 아니며 제3조②의 명시 의무를 시험한다.
- 새 스키마 필드가 빠진 live 응답은 재시도 후 기존 판정으로 돌아간다. 과거 회차는
  실행 설정으로 구 스키마를 식별해 재생하며, 관측하지 않은 새 사실을 채우지 않는다.
- 소유권·실행 보고서·카나리의 항목 목록을 같은 추가 호출에 맞춘다. e10·e18·e20은 빈칸이다.

`_company_size_bands`, `company_size_products`, A2 정규식 및 다른 항목의 판정 함수는 그대로다.
새 사실 소비는 최신 사용자 지시의 세 항목 TP 확인에 필요한 배선이다.

## 근거와 관측 경계

제공 판로지원법 제9조·시행령 제10조, 소프트웨어 진흥법 제2조·제48조,
중소 소프트웨어사업자의 사업 참여 지원에 관한 지침 제3조②를 사용했다.
원본 경로·해시는 [검사 기록](h2-check.json)에 있다. 법령을 새로 수집하지 않았다.

입력 자체의 불완전·문서 누락은 부재 증거로 쓰지 않는다. v10은 전체 가시 문서가
잘리지 않아야 한다. SW 명시 의무의 장소는 공고문 또는 제안요청서이므로 둘 다 전부
보이면 규격서 꼬리만 잘린 상황과 구분한다. 공고문/RFP가 잘렸거나 누락되면 보류한다.
이 구분은 공고 ID·dev 정답·특정 낱말 개수에 의존하지 않는다.

## 로컬 검증

세 항목의 출력 경로와 관측 경계 검사를 먼저 추가했다. 수정 전 v10·v20 출력이 없어
실패했고 수정 후 통과했다. 합성 모델 응답 검사이며 TP 측정이 아니다.
관련 unittest **45개 통과(30.629초)**, Ruff 통과. 압축 해제 mock 10건·49열,
모델 없는 기본 진입 실패도 확인했다([패키지 검사](h2-package-check.json)).
노트북 수정 뒤 package 검사 7개(22.306초)와 확장한 TP 관문 검사(7.633초)를 통과했다.
FP가 있어도 TP가 0인 경우와 셋 중 하나만 TP=0인 경우를 모두 목표 미달로 기록한다.
노트북 코드 셀 컴파일과 고정 SHA의 script 바이트 일치도 확인했다.

각 CSV는 바이트 동일·변경 0셀이다. 이는 구 응답 호환성이고 새 프롬프트의 성과가 아니다.
실제 모델 TP/FP/FN·출력 토큰·실행 시간·동일 ZIP 반복·무라벨 발화율은 전부 미측정이다.

## 실행과 통과 판단

저장소의 [A3 전용 노트북](../../../notebooks/exp-a3-source-role.ipynb)을 이 후보로 고정한다.
추론 후보는 `cc7c9719b60b84f1fe6a713969ca886044066d75`, script SHA-256은
`0f96dbb675cb942172bb8e0744ba13e69d96aea592764871f369f761e3f74d57`이다.
런타임이 종료됐다면 새 A100급 런타임에서 첫 셀부터 실행한다. HF_TOKEN 접근만 준비하고,
고정된 REPO_REF·SOURCE_MODE·RUN_DIAGNOSTIC·DIAGNOSE_ITEMS는 수정하지 않는다.
노트북은 세 항목 TP/FP/FN을 출력하며, 하나라도 TP=0이면 목표 미달로 기록한다.
목표 미달이어도 dev-debug 원응답과 마지막 결과 ZIP을 끝까지 보존한다.

세 TP가 모두 양수인 것은 첫 관문이다. 대상 밖 21항목의 TP/FP 변화, 038·043·044/039의
문장 역할, 동일 ZIP 별도 재실행 churn, 무라벨 6,000건 발화율, 시간까지 작업서 조건을
모두 확인해야 한다. 무라벨은 배포 데이터와 모델 실행이 필요한 별도 회차다.
공개 clone에는 대용량 무라벨 파일이 없으며, dev 노트북만 실행해 이 검사를 했다고 하지 않는다.
독립 리뷰·대회 제출은 하지 않았다. 노트북의 실행 성공은 성능 채택이나 서버 성공이 아니다.
