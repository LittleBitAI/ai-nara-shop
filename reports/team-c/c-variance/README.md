# C-variance — 회차 변동폭을 재서 판정의 분모를 만든다

담당 C · 2026-09-26 · 회차 실행은 사람이 한다. 이 문서는 무엇을 왜 재고 결과를 어떻게
읽을지만 정한다. 코드를 바꾸지 않는 것이 이 실험의 전부다.

## 0. 왜 이것인가

9/25 회차 `colab-1790318892216968298` 에서 같은 코드의 두 통과가 **0.7742 대 0.7398**,
12셀 · Macro **0.034367** 로 갈렸다. 기록된 같은 코드 쌍의 Macro 상한은 **0.010088** 이고
이 수는 그 **3.4배**다.

이 수가 변동폭이면 팀의 여러 판정이 분모를 잃는다. #143 의 +0.013643 도 그보다 작다.
그래서 먼저 **이 0.034 가 무엇인지** 확정하고, 그다음 변동폭을 제대로 잰다.

## 1. 판정 — (가) 같은 코드·같은 입력의 두 추론 통과다

### 1-2. `--debug-responses` 는 판정 경로를 안 탄다

`script.py` 에서 이 플래그가 실제로 분기하는 자리는 **한 곳**이다.

```python
# script.py:1214, run_chunk() 안
if debug_responses:
    fields["response_text"] = text
```

`fields` 는 진단 이벤트(`emit`)로만 나간다. 프롬프트 · 샘플링 · 예산 · 청크 크기 ·
파싱 · 후처리 어디에도 안 들어간다. 나머지 참조(`3441`·`3466`·`3496`·`3506`·`3551`·
`3574`·`3599`·`3630`·`3656`·`3778`·`3790`)는 전부 이 값을 아래로 넘기거나 기록하는 것이다.

## 3. 그래서 무엇을 재나 — 회차 설계

### 3-1. 알고 싶은 것

**"Macro 차이 0.0136 을 한 쌍의 회차로 잡음과 가릴 수 있는가."**

지금 있는 것은 같은 코드 쌍 12개(기존 11 + 이번 1)인데 **코드가 제각각이다.**
한 코드를 N회 돌린 적이 없다. 그래서 "이 코드에서 Macro 가 얼마나 흔들리나"를 못 말한다.

### 3-2. N = 6

| | |
| --- | --- |
| 통과당 소요 | 평균 **925초**(15.4분) — `dev` 942.808 · `dev-debug` 907.525 |
| 6회 추론 | 약 **93분** |
| 셋업(clone·패키지·모델 내려받기) | 별도. 같은 런타임이면 HF 캐시가 재사용된다(`docs/colab.md`) |
| 합계 | 셋업 + 약 1시간 35분 |

6회를 고른 이유.

- **쌍이 15개** 나온다(6C2). 한 쌍짜리 관측을 15개로 늘린다.
- 한 세션 안에서 끝날 분량이다. 세션이 끊기면 그 회차부터 설정이 달라질 위험이 있다.
- 0.0136 이 문제라면 이미 한 관측(0.034)이 그 2.5배다. **범위가 0.0136 을 넘는지**만
  보면 되고, 그 판정에 6회면 족하다.

### 3-3. 이 N 으로 말할 수 있는 것과 없는 것

| 말할 수 있다 | 말할 수 없다 |
| --- | --- |
| 관측 6회의 Macro **범위**(min~max) | 분포 · 표준편차 · 신뢰구간 |
| 쌍 15개의 **갈린 셀 수 범위** | 이 범위가 상한이라는 것 |
| 항목별로 **몇 번 흔들렸는지** | 다른 코드 · 다른 GPU 에서의 변동폭 |
| "X 보다 작은 차이는 한 쌍으로 판정 못 한다" | **서버** 변동폭 (한 번도 재지 않았다) |

**"분포를 추정했다"고 쓰지 않는다.** 6회는 분포를 말하기에 너무 적다. 보고는
"관측 6회의 범위"로만 적는다. 범위가 0.0136 보다 작게 나와도 "안전하다"가 아니라
**"6회에서는 그보다 큰 흔들림을 보지 못했다"** 로 적는다.

### 3-4. 고정할 것

| | 값 | 왜 |
| --- | --- | --- |
| 코드 | `origin/main` = **`e1474d1`** 그대로 | 코드를 안 바꾸는 것이 이 실험이다 |
| 입력 | `open/dev.jsonl` 200건 | 모든 통과 동일 |
| `--debug-responses` | **모든 통과에서 켠다** | §1 에서 판정 무관이 확인됐고, 원응답을 남기면 이 비싼 회차로 나중에 어떤 후보든 재생으로 잴 수 있다 |
| case 이름 | `var-01` … `var-06` | `run_case()` 가 `mkdir(parents=True)` 로 만들어 **같은 이름 재사용이 실패한다** |

## 4. 걸릴 수 있는 보호 검사

### 4-1. `check_live` 는 이 회차에 못 쓴다 — 예정된 것이다

노트북 `check_live()` 의 `expected_settings` 가 **`"debug_responses": False`** 를 요구한다.
`--debug-responses` 로 돈 통과에 부르면 `RuntimeError: 서버 기본 추론 설정 불일치` 로 죽는다.

셀 `[18]` 이 이미 그래서 `check_live` 를 안 부르고 자체 검사를 한다. 이 회차도 같은
방식을 쓴다 — 실행 카드의 셀이 `mode`·`건수`·`model_success_count`·`code_sha256`·
`input_sha256`·`debug_responses` 를 직접 확인한다.

### 4-2. 같은 이름 재실행이 막힌다

```python
def run_case(name, source, args=()):
    case = WORK / "cases" / name
    data = case / "data"
    data.mkdir(parents=True)        # ← exist_ok 가 없다
```

같은 `name` 으로 두 번 부르면 `FileExistsError` 다. 그래서 통과마다 이름을 바꾼다.

### 4-3. 과거에 회차를 중단시킨 종류

`docs/colab.md` §8 이 적는다 — 중간 셀이 실패해도 **마지막 셀(`[20]`)을 따로 실행해
로그 ZIP 을 받는다.** 추론이 이미 끝났으면 자료는 살아 있다. 이 회차도 같다: `var-0k`
하나가 자체 검사에서 죽어도 앞서 끝난 통과의 결과는 `RESULTS` 에 남아 있다.

## 5. 이 결과가 무엇을 바꾸는가 — 미리 적는다

**결과를 보기 전에 적용하지 않는다.** 아래는 결과가 나왔을 때 쓸 문장과 목록이다.

### 5-1. #143 에 대해

관측 범위가 **0.013643 보다 크면** #143 의 보고에 이 문장을 더한다.

> 이 후보의 dev 이득 +0.013643 은 같은 코드의 회차 변동폭 범위 안이다. 재생에서는
> 세 규칙이 가산적이고 대상 밖 0셀이지만, **실제 회차 한 쌍으로는 이 크기를 가릴 수 없다.**

범위가 그보다 작으면 "6회에서는 그보다 큰 흔들림을 보지 못했다"까지만 적는다.
**어느 쪽이든 #143 을 이번에 고치지 않는다.** 결과가 나온 뒤 C 가 정한다.

### 5-2. 0.034 보다 작은 차이로 판정된 과거 — A 가 볼 목록

되돌리자는 제안이 아니다. 분모가 흔들리면 다시 읽어야 할 것들의 목록이다.

**서버 제출**(`reports/submissions.json`). 서버 변동폭은 한 번도 재지 않았으므로
이 0.034 를 서버에 그대로 대면 안 된다 — dev 회차의 수다. 그럼에도 크기 비교로 적는다.

| 제출일 | 코드 | 서버 Macro | 직전 대비 | 0.034 보다 작나 |
| --- | --- | ---: | ---: | --- |
| 9/21 | `3a3016716` | 0.5057795952 | −0.0026341922 | **예** |
| 9/22 | `227631fe2` | 0.5077356078 | +0.0019560126 | **예** |

**dev 재생으로 채택·반려된 것.** `.wiki/plan-active.md` 가 소유하는 표에서 dev 이득이

이 목록의 뜻은 **"그 판정들이 틀렸다"가 아니다.** 대부분은 dev 재생(결정적)으로 쟀고
그것은 이 변동폭과 무관하다(§5-3). **회차 한 쌍의 Macro 차이로 판정한 것**만 다시 읽을
대상이다.

### 5-3. 같은 원응답 재생은 이 변동폭과 무관하다

이 실험이 재는 것은 **서로 다른 모델 실행 사이**의 흔들림이다. 같은 원응답을 두 코드로
재생하면 모델 출력이 한 글자도 안 다르므로 차이는 전부 코드의 효과다 — 결정적이다.
`reports/runs/reproducibility.md` 의 「재생 비교에는 이 값을 쓰지 않습니다」 가 그것이다.

그래서 규칙 효과를 **같은 원응답 재생으로 떼는 현재 방식이 옳다.** 이 회차가 0.034 든
0.1 이든 그 방식은 안 바뀐다. 바뀌는 것은 **회차끼리 견줄 때** 무엇을 신호로 읽느냐다.

## 6. 미확인

- **왜 갈리나.** `temperature=0` · 시드 고정인데 추론이 갈린다. vLLM 배치 구성이나
  부동소수 누적 순서가 후보이지만 이 자료로는 못 가른다. 이 회차도 그것을 답하지 않는다 —
  **얼마나** 갈리는지만 잰다.
- **6회가 최악을 봤는지.** 못 말한다. 범위는 관측된 것의 범위다.
- **서버 변동폭.** 같은 코드를 두 번 올린 적이 없다. 이 회차로도 안 나온다.
- **다른 GPU·다른 코드에서의 크기.** 이 회차는 `e1474d1` · A100 한 조합이다.
- **`dev` 와 `dev-debug` 를 같은 저울로 읽지 않는다**는 규칙과의 관계. 여기서 쓰는 것은
  두 점수의 **차이**이고 한쪽 점수를 다른 쪽으로 갈음하지 않는다. 이 회차는 그 문제를
  아예 없앤다 — **6회 전부 같은 설정**(`--debug-responses` 켬)이라 저울이 하나다.
