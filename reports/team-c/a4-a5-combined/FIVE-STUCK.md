# 안 움직인 다섯 — "공통 원인 하나"는 틀렸다

2026-09-21. 주 세션. 모델을 부르지 않았다. H4 회차 `colab-1789902969401579900` 의
`dev-debug` 원응답 200건(`company_size`)과 `open/dev.jsonl`·`open/dev_labels.csv` 만 읽었다.
재현 코드는 §6.

## 0. 먼저 — 내가 틀렸다

주 세션은 오늘 여러 번 이렇게 적었다.

> 무변화 다섯(v10·v13·v18·v20·v24)은 원인이 하나로 모인다. **한 `company_size` 호출의
> 사실을 여덟 항목이 나눠 쓰고, 그 사실이 틀리면 후처리 게이트로는 못 고친다.**

**그 문장의 뒷부분은 맞고 앞부분은 틀렸다.** 실제로 재 보니 다섯은 한 원인이 아니라
**최소 넷**이다. 근거는 §1이다.

이 문장을 "다음 한 번의 프롬프트 수정으로 다섯이 같이 움직인다"로 읽으면 안 된다.
astra 의 h3 회차가 그것을 이미 한 번 보여 줬다 — 한 번 바꾸자 v18 이 +0.229 오르고
여섯이 무너져 Macro −0.0497 이 됐다.

## 1. 다섯은 **같은 공고에서 안 틀린다**

합본(#75) 예측과 정답을 대조해 다섯 항목의 오답 공고 집합을 구했다.

| | 오답 | |
| --- | ---: | --- |
| v10 | 11 | |
| v13 | 11 | |
| v18 | 8 | |
| v20 | 8 | |
| v24 | 39 | |
| **합집합** | **65** | 단순합 77 |

```
한 공고가 몇 항목에서 틀리나 :  1항목 54건 · 2항목 10건 · 3항목 1건
```

**오답 공고의 83%(54/65)가 다섯 중 한 항목에서만 틀린다.** 쌍별 자카드는 최대 **0.12**
(v10∩v18)이고 나머지는 0.02~0.07 이다. 같은 사실이 같은 공고를 동시에 망가뜨리는 모양이
**아니다.** 공유 사실이 원인이라면 겹침이 이것보다 훨씬 커야 한다.

## 2. 입력 불완전이 원인인 것도 아니다

| 항목 | 오답 중 입력이 온전한 것 |
| --- | --- |
| v18 · v24 | **100%** |
| v10 · v13 | 91% |
| v20 | 62% |
| (참고) dev 200건 전체 | 95% |

**v20 만 입력 불완전 쪽으로 치우친다.** 나머지 넷은 온전한 입력에서 틀린다 —
자료를 더 넣어도 안 풀린다는 뜻이다. 같은 결론이 astra 의 `PPS-D-002151`(240kW 충전기)
에서도 나왔다.

## 3. 사슬이 어디서 끊기는지는 항목마다 다르다

`verify_document_requirements()` 와 같은 순서로 단계를 되짚어 정답 양성마다 세었다.

### v10 — 정답 양성 7건

| 끊긴 자리 | 건수 |
| --- | ---: |
| **6 통과 → 1** | **4** |
| 7 완전관측 검사 탈락 (`본문 절단 표시`) | 1 |
| 4 요건 있음 → 0 (부재가 아니라고 읽음) | 1 |
| 2 적용대상 인용 검증 실패 | 1 |

200건 전체로는 `1 적용대상 아님(scope=general)` 122 · `4 요건 있음` 47 ·
`6 통과` 12 · `7 완전관측 탈락` 12 · `2 인용 검증 실패` 7 이다.
**v10 의 남은 셋은 서로 다른 단계에서 끊긴다.**

### v20 — 정답 양성 5건

| 끊긴 자리 | 건수 |
| --- | ---: |
| **7 완전관측 검사 탈락** | **3** |
| 6 통과 → 1 | 1 |
| 1 적용대상 아님 (`software_business=no`) | 1 |

**v20 은 모델 판단이 아니라 게이트에서 막힌다.** 그 세 건(`131`·`134`·`24`)은
`requirements_complete=yes` · `입력 완전관측` · `문서 탈락 없음` **셋이 동시에 거짓**이다.
입력 자체가 불완전한 공고다.

200건에서 각 조건이 거짓인 비율은 이렇다.

```
v20 경로 : 공고문·제안요청서 절단 62/200 · requirements_complete 14 · 완전관측 10 · 문서탈락 10
v10 경로 : 본문 절단 표시 85/200 · 문서 누락 표시 33 · requirements_complete 14 · 완전관측 10 · 문서탈락 10
```

**절단이 가장 자주 걸리는 조건이다**(v10 경로 85/200). 다만 v10 양성에서 절단으로 막힌 것은
1건뿐이라, 이 비율을 v10 의 원인으로 바로 읽으면 안 된다.

## 4. 그래서 다섯은 넷이다

| 묶음 | 항목 | 막는 것 | 고칠 자리 |
| --- | --- | --- | --- |
| **A. 게이트가 막는다** | **v20** | 입력 불완전 3건이 완전관측 검사에 걸린다 | 게이트를 풀지 말지의 판단. 풀면 잘못된 관측도 같이 들어온다 |
| **B. 적용대상 판별이 틀린다** | **v10** · v13 | `scope` 가 정탐과 오탐에서 같은 값 | 같은 호출 안에서 지정 품목·특이사항을 **분해해** 관측 |
| **C. 라벨 기준 미상** | **v24** | 본문과 등록값이 실제로 다른데 정답 0인 반례 3건 | 라벨 정의 역공학. 네 번째 축(업종) 미측정 |
| **D. 재현율 벽** | **v18** | 오답 8건이 **전부** 온전한 입력 | 아직 원인 미분해 |

**v24 는 애초에 이 묶음이 아니다.** `company_size` 호출이 덮어쓰는 아홉 항목
(`v10 v12 v13 v14 v15 v16 v17 v18 v20`)에 v24 가 없다. 공유 사실과 무관하다.

## 5. 공유 사실 이야기 중 살아남는 부분

"한 호출을 아홉이 나눠 쓴다"는 **사실이다.** 코드로 확인된다.

```
BAND_ITEMS            v14 v15 v16 v17 v18
SCOPE_ITEMS           v12 v13
DOCUMENT_CHECK_ITEMS  v10 v20
```

살아남는 결론은 **비용 쪽**이다 — 이 호출의 프롬프트를 건드리면 **아홉이 동시에 움직이므로
한 항목을 위해 바꾸면 나머지 여덟이 대가를 치른다.** h3 회차가 그 대가를 수치로 냈다
(v18 +0.229 / 여섯 합 −0.0497).

**부정되는 결론은 원인 쪽이다** — 다섯이 한 사실 때문에 한꺼번에 막혀 있는 것이 아니다.

## 7. 이 분석이 증명하지 않는 것

- **원인을 확정한 것이 아니다.** 어느 단계에서 끊기는지를 셌을 뿐이고,
  그 단계가 왜 그 값을 냈는지는 항목마다 따로 봐야 한다.
- v18 은 **분해하지 않았다.** 오답 8건이 전부 온전한 입력이라는 것까지만 확인했다.
- §3 의 단계 이름은 `verify_document_requirements()` 를 되짚어 만든 것이다.
  그 함수가 바뀌면 이 표도 다시 세야 한다.
- dev 200건이다. 무라벨·비공개 집합에서 같은 분포라는 근거는 없다.
- 채택한 것이 없다. `script.py` 는 0줄 바뀌었다.
