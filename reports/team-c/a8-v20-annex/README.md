## 착수서 대비 정정 한 건

**예산 추정의 분모가 934자가 아니라 1,568자다.** 착수서의 `934/1.5 ≈ 623토큰, 초과 0/200`은
법령 원문만 센 추정이고, 실제로 붙는 것은 지시 머리글을 포함한 1,568자다.
같은 글자 환산을 적용하면 약 1,045토큰이 되지만 **이것도 추정이며 채택하지 않는다.**
**실제 값은 아래에서 쟀다 — 586토큰.** GPU 실행기도 생성 호출 전에 같은 계산을 다시 하고
조건을 못 채우면 멈춘다.

머리글을 줄여 블록을 작게 만들 수는 있으나, 그 문장들이 "법령을 인용 근거로 쓰지 말 것 ·
null을 금액 추론으로 채우지 말 것 · 새 필드를 만들지 말 것"을 담는다. **측정 결과 줄일 필요가
없었다** — 채택한 예산에서 최악 공고에도 428토큰이 남는다.

## OFF/ON 재생은 정적 불변이다 — 유출은 스윕이 잡는다

같은 H4 원응답(`colab-1789902969401579900/dev-debug`)을 후보 문맥 OFF/ON으로 재생하면 두 CSV가
보관 기준선(`a5-label-definition/head-replay/submission.csv`)과 **바이트 동일**하다(바뀐 셀 0,
v20 1/4/4, 혼합 Macro 0.593846165415).

**이것을 "소비 경로 배선 검사"라고 부르지 않는다.** 후보가 소비자를 안 바꾸고 재생은 프롬프트를
읽지 않으므로 바이트는 **같을 수밖에 없다.** 이 재생이 말하는 것은 `activate()`가 재생 경로에서
읽히는 것을 하나도 건드리지 않았다는 정적 불변뿐이다. 라운드 1 리뷰의 P2 지적이 옳다.

법령 문자열이 항목으로 새는지는 **결정적 소비자 스윕**이 잡는다 — 공고 200건 × 인용 필드 7개에
별표의 실제 부분문자열을 넣고 24항목을 다시 계산한다(`LawQuotationTests`).

## 고정 회차에서 도달 가능한 v20 TP 상한은 2다

착수서의 분석을 구현 기준에서 원자료로 다시 확인했다. H4 재생의 v20은 TP `133`,
FP `056·064·068·144`, FN `24·131·132·134`다.

| FN | 차단 지점 |
| --- | --- |
| 024 · 131 · 134 | 제안요청서 1건 탈락 + 완전관측 `false`. **프롬프트가 못 바꾸는 입력 사실**이다 |
| 132 | `software_business=no`. 완전관측 `true`, 문서 탈락 없음 — 주입으로 닿을 수 있는 유일한 건 |

그래서 **TP 상한은 기존 1 + 132 한 건 = 2**다. 게이트를 풀어 이 상한을 올리지 않는다.
사전 등록 기준(§5)의 `TP≥2`는 이 계산 위에 있다. Macro 상승 하나만으로 채택하지 않는다.

## 예산 — 운영 설정으로는 블록이 안 들어간다

보관 H4 진단이 실제 토크나이저로 남긴 값을 다시 읽어 찾았다. **운영 예산에서는 여유가 22토큰이다.**

| 값 | 측정 |
| --- | --- |
| company 프롬프트 토큰 | min 4,586 · median 10,941 · mean 10,370 · **max 14,250**(`PPS-DEV-091`) |
| 운영 프롬프트 예산 | `16,384 − 2,048 − 64 = 14,272` → 최악 공고에 **22토큰** 남음 |
| company 출력 토큰 | min 142 · median 270 · p95 389 · **max 494**, 200건 전부 `finish_reason=stop` |

즉 운영 `MAX_TOKENS=2048`은 **관측 최댓값의 4.15배**를 예약하고, 그 여유가 프롬프트 쪽을 막고 있었다.
블록을 700~1,000토큰으로 잡으면 25~36건이 예산을 넘어 **후보만** 문서가 깎인다 — 교란이다.

### 그래서 출력 예약을 줄인다 (두 군 공통)

`OUTPUT_RESERVED = 1024`. 예산이 **15,296**이 되고, 관측 최대 출력 494의 **2.07배**가 남는다.

| 예약 | 프롬프트 예산 | 최대 공고의 블록 여유 | 출력 494 대비 |
| ---: | ---: | ---: | ---: |
| 2,048 (운영) | 14,272 | **−** (22토큰뿐) | 4.15배 |
| **1,024 (채택)** | **15,296** | **1,014** | **2.07배** |

추정이 틀린 방향도 적는다 — 블록을 730~1,000토큰으로 봤는데 실제는 586이다. 별표의 박스
문자가 2.49자/토큰으로 예상보다 잘 묶였다. 그래도 운영 예산에서는 13건이 깎이므로 (A)는 필요하다.

최대 공고가 `PPS-DEV-189`인 것도 이 변경의 결과다 — H4에서 13,600자로 절단됐던 그 공고가
늘어난 예산에서 **두 군 모두** 절단이 풀렸다. 나머지 199건의 control은 H4와 같다.

- **사전 등록 조건은 고치지 않는다.** 「추가 축소 0/200·두 군 공고 본문 동일」을 낮추는 게 아니라

  `script.py` 수정이 따르므로 A8 범위 밖 별건이다.
- 규칙: 출력 예약은 대회가 정한 값이 아니다. R19는 패키지 버전, R4는 정상 응답을 요구하며
  관측 최댓값의 2배 예약은 그 요건을 해치지 않는다. R21 총시간은 줄어드는 방향이다.
- 재현: 고정 리비전의 토크나이저 파일만 받아(`tokenizer*`·`*.jinja`, 가중치 없음)
  `a8_v20_annex.TokenizerRunner`로 센다. **서버 고정 `transformers` 5.14.1이 필요하다** —
  4.x는 이 모델의 `tokenizer_config.json`을 못 읽는다. torch·GPU는 필요 없다.

## 예산 검사가 GPU에서 무엇을 하나

`budget_report()`가 공고 200건마다 control/후보 두 군의 **전체 메시지**를 이 런타임의
실제 토크나이저·제출 chat template으로 센다. `조항호내용` 제외 meta, 같은 products·문서 선택·
`max_chars`·입력 예산·출력 예약량을 쓴다. 남는 기록은 `budget.json`이다.

- 두 군 공통 예산 15,296으로 센다. 운영값(14,272)과의 차이도 같은 파일에 남긴다.
- 통과 조건: **추가 축소 0/200**과 **두 군 공고 본문 sha256 동일**.
- control에 이미 있던 절단은 `control_truncated`로 따로 센다. 공통 예산을 더 줄이지 않는다.
- 한 건이라도 추가 축소되면 **생성 호출 전에** 멈추고 `budget.json`만 남긴다.
- `token_count_kind != actual`이면 조건을 채워도 `budget_safety_evidence`는 거짓이다.
  mock·글자 환산은 예산 근거가 아니다.

## 실행하지 않은 것

실제 모델 호출, GPU 두 회차, 후보 시간, 무라벨 6,000건 발화율, 서버 제출.
