# 브리프 4 후속 — v18을 어떻게 시험할 것인가

2026-09-21. 앞선 독립 분석의 구현 가능한 실험 설계 보충이다.
이 문서는 효과가 입증된 수정안이나 실행 준비 완료 표시가 아니다.
운영 코드·후보·프롬프트는 아직 수정하지 않았다. 다른 세션의 고정 분석도 읽지 않았다.

## 먼저 비용 경계

기존 company_size 한 호출을 교체한다. 별도 모델 호출은 추가하지 않는다.
`6380 + (candidate_stage_seconds - 246.985) * 8.8944 <= 7200`이므로
단계 계획 상한은 339.178초/200건이다. 새 출력의 실제 시간은 미측정이다.
기존 H3 294.115초에서 출발하면 단계 여유는 약 45.063초이며,
기존 H4 대비의 92.193초를 H3에 다시 더하면 안 된다.

## 한 가설

공유 scope를 통째로 대체하지 않고, 같은 응답에 범위 재검토 결과를 따로 받아
v18에만 소비하면 TP 회복과 다른 항목 손실을 분리할 수 있는가.

동일 응답 안의 필드를 나누는 설계다. 배포 시 control 응답과 candidate 응답 두 개를
얻어 합치는 설계가 아니다. 저장된 서로 다른 응답의 좋은 칸만 모은 성능을 약속하지 않는다.

## 입력·출력 변경을 고정한다

1. 문서 선택·제공 고시 조회·문자 예산 정책·모델·샘플링·기존 필드 정의는 유지한다.
   출력 토큰 제한도 먼저 유지하고, 한도에 걸리면 실패로 기록한다.
2. 기존 company_size 스키마 뒤에 `scope_review`와 `scope_review_quote`를 추가한다.
   앞 필드는 기존 scope와 같은 `general/competitive/other/unknown`, 뒤는 원문 인용 또는 null이다.
   quote 길이는 기존 인용 필드 제한을 재사용한다.
3. 추가 지시는 기존 필드 뒤의 별도 재검토 결과를 요구한다. 질문은 구매 목적물과
   제공 고시의 지정 범위·특이사항이 실제로 일치하는지다. 도구/부품의 언급, 제목 유사성,
   메타 코드 부재만으로 분류하지 않고, 혼합 구매와 조건 미관측은 unknown으로 남긴다.
   위반 여부나 dev 공고 번호·정답은 묻거나 넣지 않는다.
4. 기존 scope와 재검토 scope가 다를 때 어느 근거로 달라졌는지 원문/제공 고시를 감사한다.
   코드에서 “새 값이 더 정확하다”고 가정하지 않는다. 같은 사업의 분류가 서로 다른 것은
   임시 실험의 비교 대상이며 최종 운영에서 설명 없이 영구화할 계약이 아니다.

출력 순서를 뒤에 둔다고 기존 필드가 보존되는 것은 아니다. 프롬프트 입력 자체가 달라지므로
기존 qualification·priority_exception·scope 등이 흔들리는지도 반드시 측정한다.
이번에는 H3 조건 관측 필드 전체나 다른 소비 규칙을 함께 추가하지 않는다.

## 소비 방법 — 기존 검증 함수를 두 번 계산하되 모델 호출은 한 번

후보 wrapper는 다음 순서만 수행한다. 모두 모델 뒤 CPU 작업이다.

```text
legacy = 기존 verify_company_size(기존 필드, 공고, 실제 max_chars)
reviewed_facts = 기존 필드의 복사본
reviewed_facts.scope = scope_review
reviewed_facts.scope_quote = scope_review_quote
reviewed = 기존 verify_company_size(reviewed_facts, 공고, 실제 max_chars)

결과 = legacy의 복사본
reviewed에 v18 판정이 있으면 결과의 v18만 교체
reviewed에 v18 판정이 없으면 legacy의 v18을 유지
다른 항목에 대한 reviewed의 결과는 사용하지 않음
```

이렇게 기존 인용 복원·원문 대조·카탈로그 veto·금액·자격 역할·예외·완전관측 검사를
전부 재사용한다. unknown/null/검증 실패는 일반제품 또는 부재로 바꾸지 않는다.
유효한 검토 결과가 v18=0을 반환하면 0도 반영한다. 0→1만 허용하는 점수 맞춤 패치는 하지 않는다.
legacy/reviewed의 반환 reason과 v18 덮어쓰기 여부를 따로 기록한다.

이 설계로 038의 자격 모순, 044의 여러 차단, 22의 절단을 해결했다고 주장하지 않는다.
그 차단들을 이번에 완화하지 않는다.

## CPU에서 먼저 통과시킬 것

- 저장 H4 응답에 새 필드가 없을 때 기존 CSV를 바이트 동일하게 재현한다.
- H3 저장 응답의 scope를 재검토 필드 대역으로 사용해 wrapper를 검사한다.
  이는 배선 검사이며, 아직 존재하지 않는 새 프롬프트의 성능으로 기록하지 않는다.
- 같은 후보 응답에서 재검토 소비를 끈 결과와 켠 결과의 v18 밖 23항목 차이는 0셀이어야 한다.
- 무효 인용/unknown은 기존 결과를 보존하고, 기존 범위·자격·절단 게이트가 계속 적용되어야 한다.
- 등록된 H3의 전역 scope 교체에서 생긴 v10 FP +16이 선택적 소비로 전달되지 않는지 확인한다.
  새 프롬프트가 legacy 필드 자체를 바꾸는 문제는 이 CPU 검사로 증명할 수 없다.

기존 `experiments/a5_scope_pilot.py`의 수집·재생·회차 기록과
`tools/replay_run.py`/`tools/score.py`를 재사용한다. 새 실행 프레임워크는 만들지 않는다.
실험 후보 wrapper와 필요한 실행기 분기만 후속 구현 범위로 둔다.

## GPU에서 무엇을 가르는가

동일 dev 200건 전체에 control/후보를 실행한다. 별도 새 런타임 반복은 순서를 뒤집는다.
회차 1 control→후보, 회차 2 후보→control. 기존 baseline/SME는 양쪽에서 같은 저장 응답을 쓴다.
각 후보 응답은 다음 두 가지로 재생한다.

| 비교 | 확인하는 것 |
| --- | --- |
| 후보 응답, 재검토 소비 OFF ↔ ON | 같은 사실에서 v18 소비 배선의 효과. 다른 23항목은 동일해야 함 |
| control ↔ 후보 응답, 재검토 소비 OFF | 추가 질문이 기존 사실을 훼손했는지. 서로 다른 추론이므로 반복 변동 포함 |
| control ↔ 후보 응답, 재검토 소비 ON | 실제 배포 구조의 전체 효과. 보호된 것처럼 보이게 control 필드를 끼워 넣지 않음 |

결과를 보고 고르는 대신 다음 기준으로 판정한다.

- CPU 계약 위반·파싱/출력 실패·단계 시간 상한 초과는 실행 후보 실패다.
- dev 진행 기준: 두 회차 각각 v18 TP≥3, FP는 같은 회차 control 이하이며,
  scope/인용의 개선 근거가 원문과 제공 고시로 설명돼야 한다. 040·041 두 ID만 맞춘 것은 통과 사유가 아니다.
- 다른 항목의 TP 감소 또는 FP 증가가 양 회차에서 반복되면 채택하지 않는다.
  한 회차에서만 회귀하거나 결과 방향이 엇갈리면 보류한다. 과거 churn 최대치로 자동 면제하지 않는다.
- 위 조건은 다음 검증으로 갈 기준이다. 작은 dev 200건만으로 최종 채택하지 않는다.
  다음에는 신규 필드를 포함한 무라벨 사실 수집과 발화율/오답 근거 감사,
  전체 파이프라인 GPU 실행이 필요하다. 서버 성과는 별도로 측정해야 한다.

모든 군/소비 경로의 24항목 F1·precision·recall·TP/FP/FN, 변경 ID·셀, 원응답,
실제 max_chars, 인용 검사, 실패/재시도, 환경·소스/입력 해시, 단계 시간과 서버 환산을 기록한다.
이 단계의 F1은 company GPU 응답을 끼운 혼합 재생 값으로 표시한다.

## 현재 완료 범위

독립 원인 분석과 이 설계까지 완료했다. 후보 구현·CPU 계약 검사·새 GPU 회차는 미실행이다.
앞 분석 라운드의 “운영 코드·후보·프롬프트를 고치지 않는다”는 경계를 유지했다.
이 문서가 그 경계를 넘어 구현까지 끝냈다는 뜻은 아니다.
