## 목적과 실행 대상

H2는 같은 H4 원응답 CPU 재생에서 v11 TP +2·FP +1, 다른 23항목 변화 0이었다.
남은 검증은 **무라벨 20,000건에 대한 H2 규칙 발화 건수·비율·dev 대비 배율**이다.
새 프롬프트를 만들지 않고 기존 `company_size` 한 단계의 사실만 수집한다.
전체 합동 판정·sme 단계는 이 진단에 필요 없어 실행하지 않는다. 추가 의존성도 없다.

- 노트북: [colab-a5-facts.ipynb](../../../notebooks/colab-a5-facts.ipynb).
- 수집기: [a5_collect_facts.py](../../../experiments/a5_collect_facts.py).

  노트북 `REPO_REF`에 이미 고정했다. `main`이나 움직이는 브랜치로 바꾸지 않는다.

## Colab에서 실행

1. 위 노트북을 Colab에서 열고 **A100 GPU 런타임**을 선택한다. 사전 검사는
   VRAM 30GiB 이상·디스크 80GiB 이상이다. 이 검사가 실제 적재 성공을 보장하지는 않는다.
2. 제공 원본 `train_unlabeled.jsonl`을 Google Drive의 `MyDrive/a5/train_unlabeled.jsonl`에 둔다.
   PC 저장소의 `open/train_unlabeled.jsonl`(790,790,220바이트)을 Google Drive 웹 화면에서
   **내 드라이브 → a5 폴더**로 업로드한다. 폴더가 없으면 만든다. 업로드 완료 후 실행한다.
   원본은 **Git 추적 제외 파일**이라 clone에 포함되지 않는다.
   이미 다른 Drive 폴더에 있다면 입력 확인 셀의 `UNLABELED_PATH`를 실제 위치로 바꾼다.
   노트북이 아래 해시와 20,000건을 확인한다.
3. Colab 보안 비밀 `HF_TOKEN`에 모델 접근 권한이 있는 읽기 토큰을 등록하고 접근을 허용한다.
4. **위에서부터 모두 실행**한다. `SHARDS_PER_EPISODE=1`을 유지한다.
   첫 회차는 dev 200건과 파일 순서상 무라벨 첫 1,000건이다.
5. 마지막 셀이 내려주는 `a5-facts-results-*.zip`을 보관·전달한다. 실패했어도 마지막 셀을 실행한다.
6. 같은 코드·GPU 환경·Drive 경로로 첫 셀부터 다시 실행하면 **다음 미완료 1,000건**을 수집한다.
   완료된 dev·무라벨 묶음은 재실행하지 않는다. 기본 설정으로 전체 무라벨은 20회다.
   `summary.json`의 `complete=true`, dev 200·무라벨 20,000건을 확인해야 수집 완료다.

무라벨 SHA256:
`f46449fb84f980a5ddf868d66f5daff2bcf0991135d9b81da5656dd607275698`.

Drive 저장 위치는 `MyDrive/a5/h2-facts-<실행 SHA 앞 12자리>/`다.
같은 폴더를 두 런타임에서 동시에 실행하지 않는다. 모델·코드·입력·환경이 달라지면 혼합을
거부하므로 같은 환경으로 돌아오거나 별도 폴더에서 처음부터 실행한다.
불완전한 1,000건 묶음은 재수집하며 그때의 오류·원응답 이벤트도 남는다.

### 첫 입력 누락 회차 복구

`a5-facts-results-1789946010020199302.zip`은 코드 `c24f208` clone/fetch/checkout 성공을
기록했다. 사용자 traceback은 Drive 입력 경로의 `FileNotFoundError`이며 ZIP에는
설치·GPU 검사·모델 추론 로그가 없다. 모델 실행 실패나 모델 성능 결과가 아니다.
로컬 원본의 위 크기와 SHA256은 다시 확인했다. Drive 전체에서 파일이 없는지까지는 모른다.

노트북에서 코드 준비와 입력 확인 셀을 분리했다. 입력 누락이면 업로드 위치를 안내하고
`input-check.json`에 기록한다. 파일을 올린 뒤 **Drive 입력 확인 셀부터** 다시 실행한다.
기존 노트북을 계속 쓴다면 실패한 셀의 git 명령부터 재실행하지 말고,
`from google.colab import drive`부터 셀 끝까지만 새 셀에 복사해 실행한 뒤 다음 셀로 진행한다.
수집 코드·프롬프트·고정 실행 SHA는 그대로다.
수정한 노트북의 코드 셀 전체 구문 검사와 입력 확인 셀의 파일 누락·잘못된 해시 거부,
실제 원본 20,000건 통과를 로컬에서 확인했다. 이 검사는 Colab/GPU 실행 증거가 아니다.

## 시간 예산 — 회차 설계 전에 확인한 값

[선계산](time-budget.json): H4 dev 순수 단계 시간 합계 716.485초를
`/200 ×1853 ×0.96`으로 환산하면 서버 6,372.704초다. 서버 실측 6,380초,
상한 7,200초, 여유 **820초**이며 허용되는 추가 dev 추론은 **92.193초**다.
새 전건 호출 +1,637초는 총 8,017초가 되므로 넣지 않는다.
H2는 후처리만 바꿔 **추가 모델 호출·프롬프트/스키마 변경 0**이다.
이 GPU 수집을 서버 파이프라인에 추가하지 않는다. CPU 재생 시간을 추론 식에 넣지 않았다.

수집 자체는 H4 A100의 company_size 200건 **246.985초**를 참고한다.

| 범위 | 단순 환산 추론 시간 |
| --- | ---: |
| 첫 dev 200 + 무라벨 1,000 | 1,481.91초, 약 24.7분 |
| 다음 무라벨 1,000 | 1,234.925초, 약 20.6분 |
| 무라벨 20,000 전체 | 24,698.5초, 약 6.86시간 |

설치·다운로드·모델 적재 시간은 별도이며 공고 길이·GPU에 따라 달라진다.
각 묶음 시작 전에 저장된 단계 시간의 최대 건당 값으로 다음 묶음을 예상하고,
25% 여유와 현재 수집기 경과시간을 합쳐 7,200초를 넘으면 중단한다. 첫 기준은 위 H4 값이다.
이는 **진단 회차 운영을 위한 예상 검사**이고 하드 타임아웃이나 서버 시간 통과 증거가 아니다.
`SHARDS_PER_EPISODE`를 늘려도 이 검사를 유지하며, 중단 시 완료분을 보존한다.

## 결과 해석과 검증

`summary.json`은 현재 완료 범위의 dev·무라벨 발화 건수/비율과 배율을 낸다.
dev 발화 0이면 배율은 `null`이다. 새 dev 단독 company_size 추론과 같은 조건으로 비교하며,
기존 H4 CPU 재생의 3/200을 새 회차의 분모처럼 섞지 않는다.
무라벨 1,000건 등 부분 수집은 20,000건 통과 조건을 대신하지 않는다.
**발화율은 최종 v11 양성률·정밀도·F1이 아니다.** 발화 사례의 원문·scope 오인도 검토해야 한다.

완료 JSON은 원응답·실제 max_chars·토큰 수·H2 발화·단계/추론 시간·환경·소스 SHA를 담는다.
입력/코드/제공 자료/모델/설정 계약과 결과 해시를 재개 시 검사한다.
응답 실패는 기존 파서·재시도를 거치고 여전히 실패하면 예외로 중단한다. 빈값/0 대체는 없다.
전체 baseline·sme 원응답이 없으므로 이 자료를 `replay_run.py`의 완전한 회차로 취급하지 않는다.

CPU 검사: `python -X utf8 -m pytest -q tests/test_a5_collect_facts.py`.
동일 company_size 프롬프트·스키마, 등록 제한값 제외, 실제 파서·재시도,
dev+1,000건/다음 1,000건 재개, 실패한 묶음 미저장, 변조 거부, 부분 집계·배율을 검증했다.
노트북 코드 셀은 모두 구문 검사했다. **실제 모델 적재·GPU 추론·서버 제출은 미실행**이다.

게시 전 관련 회귀 검사까지 합친
`python -X utf8 -m pytest -q tests/test_a5_collect_facts.py tests/test_replay_run.py tests/test_company_size.py tests/test_competitive_product.py`
결과는 **33 passed (10.87초)**다. H1/H2 후보 self-check도 통과했다.
기존 전체 검사에서 관측한 설치 테스트 실패는 [H1 기록](README.md)에 남으며 이번 범위에서 고치지 않았다.
