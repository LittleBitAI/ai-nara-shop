# A5 브리프 4 — 다섯 항목 무변화의 독립 분석

2026-09-21. 회차 ID `a5-brief4-independent-cpu`, 기준 main `434f518`.
`docs/five-stuck-analysis` 브랜치·분석문은 읽지 않았다. 이 분석은 저장 응답의 CPU 재생이며
새 GPU·서버 점수가 아니다. 운영 코드·후보·프롬프트 변경 0, 모델 호출 0.

**무변화의 직접 원인은 하나다. 이번 후보들이 이 다섯의 최종 판정을 바꾸지 않았다.
하지만 낮은 F1의 원인은 하나가 아니다.** A4의 실제 변경 항목은 v6·v9·v23,
H2는 v11이다. 동일 원응답에서 다섯 항목의 **1,000셀 모두 동일**하다.
반올림이나 TP/FP 교환의 상쇄가 아니다. 후보가 아직 `script.py`에 채택되지 않은 사실과도
구분한다. 이번 비교는 후보를 실제로 얹은 재생끼리의 비교다.

## 2. 항목마다 막힌 층

### v10 — 사실의 구별력과 문장 역할, 일부 관측 실패

TP 4·FP 8의 **12건 모두** 검증된 competitive scope, `direct_production_quote=null`,
`requirements_complete=yes`, 실제 완전관측을 통과해 company 소비자가 1을 썼다.
12건 중 11건은 baseline이 0이었다. 따라서 이 오탐들은 baseline의 잘못을 그대로
보존한 결과로 설명할 수 없다. 현재 소비하는 사실 조합으로 TP와 FP가 갈리지 않는다.

미탐 3건은 서로 다르다.

| FN | 실제 차단 | 해석 |
| --- | --- | --- |
| 069 | competitive 인용·null은 통과, 실제 입력 절단으로 완전관측 실패 | 입력/관측 게이트. 부재를 확정할 근거가 부족하다 |
| 075 | 원문에 있는 직접생산증명서 인용으로 소비자가 **0을 씀** | 단어 누락이 아니다. 제출서류의 존재를 참가자격 요건 존재로 소비하는 의미 문제 |
| 13 | scope 인용 검증 실패, requirements_complete=no도 존재 | 먼저 적용 대상 검증에서 막힌다. 인용만 고치면 해결된다고 할 수 없다 |

075 D0의 직접생산증명서는 “제출서류 : 제안 요청서 참조” 아래 있고,
바로 뒤에 “상기 신청서류 누락 시 제안서평가에서 제외됨”도 있다.
“목록이니 무조건 무시”도 근거가 부족하다. 라벨은 1이고 현재 소비자는 0이다.
**참가자격 조항과 제출서류의 효력을 어떤 기준으로 구별하는지**가 미확정이다.
기존 직생 정규식 후보를 다시 제안하지 않는다.

### v13 — 두 검증 경로의 합성, 사실/라벨 구별력, 선택적 재검증

`baseline → 양성만 SME 재검증 → company → 후처리` 순서다.
company의 v13은 조건을 만족하면 1을 쓰지만, 불충족을 확정 0으로 쓰지 않는다.
후행 경로가 무응답일 때 앞 경로의 양성이 남는다.

- 최종 양성 13건 중 company가 1을 쓴 것은 **9건(TP 3, FP 6)**.
  나머지 **4건(TP 1, FP 3)**은 앞 단계의 양성을 보존했다.
- SME가 0으로 내렸는데 company가 되살린 것은 **5건**:
  TP 077·078·16, FP 184·198. company 덮어쓰기를 없애는 것도 해결이 아니다.
- FP 192는 baseline 0이라 SME 호출이 없었고, company가 새로 1을 썼다.
- FP 03은 company scope=general인데 앞 단계의 v13=1이 남는다.
  경로 간 불일치의 실제 사례지만, 모든 불일치에서 company를 정답으로 간주할 수는 없다.
- FN 074는 baseline 1 → SME 0 (`unverified_small_only_clause`) → company 무응답이다.
  company에는 small_only가 있어도 기존 직생 요구/카탈로그 연결이 성립하지 않았다.
- FN 076은 baseline 0이라 SME 호출이 없고 company는 sme_allowed를 냈다.
  원문 한 조항에 “중소기업 또는 … 소상공인”과 “소기업·소상공인 확인서”가 함께 있다.
  이 둘을 하나의 등급 enum으로 압축할 때 기준이 필요하다.

따라서 “v13는 company 사실만 바꾸면 된다”도, “모두 라벨 오류다”도 과장이다.
검증 우선순위는 CPU로 조사할 수 있으나 이미 기각한 여섯 축만으로 9 FP를 제거할 근거는 없다.

FP 둘이 폐기물 관련 용역이라는 제목만으로 예외를 확정하지 않았다.
현재 사실을 소비한 경로는 확인했지만 이 둘의 법적 예외/라벨 근거는 아직 확정하지 못했다.

### v20 — SW 적용 대상과 누락 문서, v18과 다른 완전관측 검사

최종 양성 **5건(TP 133, FP 056·064·068·144)** 모두 company가 1을 썼다.
SW 사업 yes + 원문 인용 + 참여제한 인용 null + software_complete가 같았다.
사업금액별 참여 기준을 소비자가 별도로 비교하지 않고, 참여 조항의 인용 유무로 압축한다.

미탐 중 **131·134·24 세 건**은 SW 적용 대상 자체는 통과한다. 그러나 실제 입력에
**제안요청서 1건 탈락, 완전관측 false**, 모델 requirements_complete=no가 있다.
문서가 없는데 프롬프트만 바꿔 내용 부재를 확정할 수는 없다.
나머지 **132**는 software_business=no라 적용 대상에서 막힌다.
전체 입력은 절단됐지만 software_complete는 **true**이므로 이 FN을 완전관측 실패로 세면 틀린다.
원문은 사무기기 임차·유지보수·OS 제공과 업종 1468 등록을 포함한다.
이를 참여제한 대상 SW 사업으로 볼 범위는 별도 의미 판단이지 “1468 언급이면 yes” 규칙이 아니다.

company의 반환 reason이 `outside_general_scope`여도 v20은 별도로 계산된다.
그 reason만 집계하면 SW의 실제 차단 지점을 잘못 분류한다.

### v24 — company와 무관한 baseline 사실·소비 경로, 미확정 비교 기준

v24는 **company 소비 대상이 아니다.** baseline 판단과 기존 후처리만 사용한다.
같은 원응답을 재생하므로 A4/H2나 company 프롬프트의 변화로 v24가 나아질 경로가 없다.
기존 후처리가 baseline 양성 8건을 내린 뒤 TP 5/FP 36/FN 3이 남았다.

FP 36건 중 원응답부터 근거가 빈 것은 **4건**, 최종 근거가 빈 것은 **22건**이다.
즉 18건은 원응답에 근거가 있었지만 원문 검증에서 지워졌다. 빈 근거여도 양성은 남는다.
TP도 원응답 빈 근거 1건 → 최종 2건이다. 이미 실패한 “빈 근거면 0”을 재제안하지 않는다.
FP 중 모든 정답 항목이 0인 공고는 **15건**이다. 다른 실행의 16건을 가져오지 않는다.

#### 네 번째 축: 면허업종 등록값 대 본문

200건 전체에서 명시적 `업종코드`+4자리와 메타 괄호 코드를 검색한 뒤 차이 사례를 원문 대조했다.
이 검색은 후보를 찾는 수단이며 업종 자격의 완전한 파서가 아니다.

- 메타·본문 모두 코드가 있는 단순 집합 차이는 061·079·191 세 건.
  **061은 “9901 또는 9999”**, **191은 “9901) 또는 … 9902)”**의 뒤 코드를
  단순 검색이 놓친 것이다. 원문상 차이가 아니다.
- 남은 **079: 등록 5246 / 본문 5210**은 실제 코드 불일치다. 이미 v24 TP이므로 신규 TP 0.
- 메타 목록이 없고 업종제한여부=N인데 본문 코드가 있는 건은
  **06·26·30·044·055·056·119**, 7건 중 v24 양성은 **055 한 건**이다.
  따라서 목록 null을 비교에서 제외하면 055라는 FN 후보를 놓친다.
  하지만 26·30·056도 본문에서 학술연구용역 1169 등록을 실제 참가자격으로 요구하며 라벨은 0이다.
  단순 “N 대 본문 업종 요구”는 **1/7**밖에 가르지 못한다.
- FN **049**는 등록/본문 모두 1261 OR 1263이다.
  FN **29**도 1253 AND 6728과 차량·장비 보유 시 1253 단독의 예외가 양쪽에 있다.
  코드 집합만으로 이 둘의 정답 사유를 확정하지 못한다.

업종 축이 존재한다는 것과 좋은 v24 규칙을 얻었다는 것은 다르다.
누락 등록과 본문 요구의 차이를 언제 위반으로 라벨링하는지는 아직 설명되지 않는다.
네 번째 축에서도 즉시 채택할 CPU 규칙을 얻지 못했다.

## 3. H3는 무엇을 움직였나 — 저장 응답의 필드별 소비 실험

등록 회차 `a5-scope-1789959906563639676/pilot/episode-1`의 control/h3 응답으로
기존 baseline·SME를 고정한 head-hybrid CSV 두 개를 **바이트 동일하게 재현**했다.
이는 위 H4 HEAD와 다른 모델 응답이다. control의 v10/v13 FP부터 각각 9/10으로 다르다.

추가로 control 사실 중 한 묶음만 h3 값으로 교체했다. 각 공고의 control `max_chars`를 유지했다.
scope 34건, qualification_role 16건, qualification 11건, priority_exception 38건이 바뀌었다.
control/h3의 실제 문서 예산도 **7건 다르다**.
아래 합성은 **소비 코드의 의존성 검사**다. 배포 가능한 규칙, 프롬프트 인과효과,
새 GPU 성능이 아니며 행별 효과를 더할 수 없다.

따라서 “조건 관측이 좋아졌으니 company 전체를 교체”는 지지되지 않는다.
단, 동일 프롬프트 별도 반복이 등록되지 않아 관측 차이를 프롬프트 효과와 churn으로 완전히 분리하지 못한다.

## 4. CPU와 GPU의 경계, 다음 한 가지

**다음 하나는 v18 적용범위(scope와 원문 인용)부터 잡겠다.**
라벨 수가 작은 상황에서 점수가 오를 것이라는 기대보다, 저장 응답으로 **040·041의
TP 회복 경로가 이미 분리됐고**, FP 증가 경로도 따로 찾았다는 점을 선택 근거로 삼는다.
v18은 현재 FP를 전부 없애도 F1 0.25라 TP 회복이 필요하다.
v13/v24는 곧바로 쓸 구별 기준이 없고, v20 FN 4건 중 3건은 실제 문서가 없다.

이 선택은 H3 scope를 전역 채택하자는 뜻이 아니다. 이미 그 경우 v10 FP +16을 측정했다.
다음 가설은 **v18의 적용범위 관측을 목적별로 분리하되 기존 아홉 항목에 대한 사실 계약을
보존할 수 있는가**다. 별도 전건 호출을 추가하는 설계는 선택하지 않는다.
단순히 새 필드 이름을 붙인다고 기존 출력이 보존된다고 가정하지도 않는다.
구현은 이번 분석 범위 밖이며 아직 후보·실행 패키지를 만들지 않았다.

| CPU로 판단/검증 가능 | GPU가 필요한 부분 또는 GPU로도 못 메우는 부분 |
| --- | --- |
| 저장 사실의 덮어쓰기 순서, 정확 인용, 실제 절단/탈락, 필드별 소비 분해 | 바꾼 scope 질문이 실제 모델에서 더 정확한 사실을 내는지 |
| v13 경로 간 불일치·소비 우선순위 및 v24 업종의 원문 대조 | 새 프롬프트/스키마의 실제 사실·처리시간·동일 설정 반복 churn |
| 기존 자료로 후보의 법령/라벨 해석을 검토하고 소비 계약 검사 | 누락된 RFP의 내용과 미확정 라벨 근거는 GPU 호출만으로 확보할 수 없음 |
| 후처리 후보를 만든 뒤 저장 응답 및 확보된 무라벨 사실로 발화율 계산 | 새 관측 필드를 쓰는 후보의 무라벨 모델 사실 수집 |

새 GPU 질문을 구체화하면 동일 입력 control/후보에서 v18 적용범위·인용 오류가 줄고
다른 23항목의 TP/FP/FN을 악화시키지 않는지, 같은 설정 별도 반복에서 유지되는지를 묻는다.
이는 미래 성능의 약속이 아니다. 선택 기준을 고정하고 24항목을 모두 기록해야 한다.

시간 경계는 기존 실측 서버 **6,380초**, 한도 **7,200초**, 여유 **820초**다.
환산계수 `(1853/200)×0.96=8.8944`이므로 company 단계는
`246.985 + 820/8.8944 = 339.178초/200건` 이내가 계획 상한이다.
등록 H3는 294.115초, 조건부 서버 6,799.195초로 남는 여유는 약 **400.805초**다.
H3 위에 다시 820초를 쓸 수 없다. 실제 서버 완주/점수는 이 환산으로 증명되지 않는다.
