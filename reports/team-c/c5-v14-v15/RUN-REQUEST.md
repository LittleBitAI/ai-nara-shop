# A 실행 요청 — v14 · v15 · v17 진단 회차

요청자 C · 2026-09-18 · 승인됨(A) · **아직 실행되지 않았다**

**이 회차는 제출 후보를 만들지 않는다.** 서버 시간 예산(여유 1,008초)과 무관한 별도 진단이며
`script.py`·`submission.csv` 를 바꾸지 않는다.

## 1. 노트북에서 바꿀 것 — 한 줄이다

`notebooks/colab-baseline.ipynb` **셀 18** — 마크다운 제목 `## 9. 항목 진단 전용 회차 (선택)`
(셀 17) 바로 아래의 코드 셀이다. 그 셀 **후반부**에 이 줄이 있다.

```python
DIAGNOSE_ITEMS = ""       # 예: "v16,v18,v20". 비우면 건너뜁니다.
```

이것을 이렇게 바꾼다.

```python
DIAGNOSE_ITEMS = "v14,v15,v17"
```

**그 밖에는 아무것도 바꾸지 않는다.**

| 스위치 | 값 | 어디에 | 이유 |
| --- | --- | --- | --- |
| `DIAGNOSE_ITEMS` | `"v14,v15,v17"` | 셀 18 후반부 | 이번 회차의 유일한 변경 |
| `DIAGNOSE_IDS` | `""` (그대로) | 셀 18, 바로 아랫줄 | dev 200건 전체 |
| `RUN_DIAGNOSTIC` | `False` (그대로) | **같은 셀 18 맨 위** | dev 재실행은 이 회차에 필요 없다 — 모델 로드 포함 15분이 더 든다 |

**`RUN_DIAGNOSTIC` 은 별도 셀이 아니라 셀 18 맨 줄에 있다.** 두 블록은 서로 독립된 `if` 라
`RUN_DIAGNOSTIC=False` 로 두어도 항목 진단은 돈다.

### 첫 셀부터 실행한다 — 셀 18 만 돌리면 실패한다

셀 18 은 앞 셀이 만든 이름을 쓴다. 소스로 확인했다.

| 이름 | 정의 셀 |
| --- | --- |
| `RESULTS` · `WORK` · `PYTHON` · `run_logged` · `write_json` | **1** |
| `SUBMISSION` | **4** |
| `MODEL_DIR` | **10** |
| `run_case` | 12 (`RUN_DIAGNOSTIC=True` 일 때만 쓰인다) |

`docs/colab.md` 도 "최신 노트북을 다시 열고 **첫 셀부터** 새 작업 폴더로 실행한다" 고 적는다.

### 셀이 실제로 만드는 명령

**노트북 소스에서 그대로 옮겼다.** 손으로 칠 필요는 없다.

```bash
python -X utf8 <WORK>/tools/diagnose_items.py \
  --items v14,v15,v17 --ids "" \
  --input     <WORK>/open/dev.jsonl \
  --data-dir  <WORK>/open/data \
  --labels    <WORK>/open/dev_labels.csv \
  --model-dir <MODEL_DIR> \
  --script    <SUBMISSION>/script.py \
  --output-dir <RESULTS>/diagnose
```

**`--script` 가 제출 ZIP 을 푼 `script.py` 를 가리킨다** — 저장소 루트의 사본이 아니다.
`manifest.json` 의 `script_sha256` 은 그 파일의 해시이며, 이 회차가 어느 코드를 읽었는지의
증거다. 환경은 `HF_HUB_OFFLINE=1`·`TRANSFORMERS_OFFLINE=1` 로 격리되므로 모델은 앞 셀에서
이미 내려받혀 있어야 한다.

## 2. 회차 ①·②·③ 과 섞지 않는다

**한 회차에 한 변수다.**

| | 이 회차에 넣나 | 왜 |
| --- | --- | --- |
| 회차 ① 근거문구 null 해제 diff | **아니오** | `script.py` 변경이고 B 판단 대기다. 이 회차는 `script.py` 를 읽기만 한다 |
| 회차 ② 출력 4칸 | **아니오** | 별도 변수 |
| 회차 ③ 3항목 별도 호출 | **아니오** | 채택 후보가 아니다 |
| `--products` (경쟁제품 카탈로그) | **아니오** | 내 `diagnose-inject-products.diff` 는 아직 `tools/` 에 안 들어갔고, 넣으면 이 회차의 변수가 둘이 된다 |

`--products` 는 v14·v15·v17 의 적용 대상 가르기(경쟁제품 제외)에 쓸모가 있을 수 있지만,
**기준선을 먼저 잡는다.** 세 항목 다 별도로 물어본 적이 한 번도 없다.

**v17 을 넣는 것은 변수를 늘리는 것이 아니다.** 세 항목이 같은 조문 계열
(판로지원법 시행령 제2조의2①)이고 구간만 다르며, 바뀌는 것은 `DIAGNOSE_ITEMS` 한 줄이다.
항목은 각각 독립적으로 집계된다. 근거는 [C1 보고서](../c1-v17/README.md#10-다음--ab-에게-필요한-전달).

## 6. 이 회차가 답하는 것 / 답하지 않는 것

**답하는 것.**

1. v14·v15·v17 을 별도로 물으면 TP 가 나오나. 제출 파이프라인은 FN 이 각각 8·6·3 이다.
   **v17 은 오탐이 문제다** — TP 3 에 FP 42 이고, 그 42건 중 40건이 이미 금액 구간 안이다
   ([C1](../c1-v17/README.md)). 이 회차는 그 40건이 어느 단계에서 켜지는지를 본다.
2. **놓친 양성이 어느 단계에서 막히나.** 이것이 이 회차의 핵심이다 —
   `context_not_observed` 면 참가자격 문구를 못 본 것이고, `condition_not_met` 면
   보고도 금액 구간·기업 범위를 잘못 맞춘 것이다. **처방이 갈린다.**
   앞 회차에서 v16 은 FN 5건이 전부 `context_not_observed`, v18 은 전부
   `condition_not_met` 이었다. 같은 처방을 쓰면 안 되는 사례가 이미 있다.
3. [조건표](README.md)의 금액 구간이 이 항목에서도 TP 를 안 지우나.

**답하지 않는 것.**

- **제출 점수.** 별도 질의는 제출 파이프라인이 아니다. 두 회차의 값이 4배 가까이 달랐다.
- **게이트 채택 근거.** 구간은 양성을 지우는 방향으로만 작동해 FN 8·6·3 을 고치지 못한다.
  v17 은 구간이 FP 를 42→40 으로만 줄이는 것까지 이미 쟀다.
- 전체 Macro F1. 0.003 이하는 회차 잡음이다.

## 6-1. 해석 기준 — **회차 전에 고정한다**

결과를 보고 나서 해석을 고르면 그것은 측정이 아니다. 아래는 **돌기 전에** 적는다.
회차가 오면 이 표를 그대로 적용하고, 표에 없는 답이 나오면 **"표에 없다"고 적는다.**

### 놓친 양성(FN)이 막힌 단계로 무엇을 결론하나

`analyze_diagnose.py` 의 `**놓친 양성이 막힌 단계**` 줄을 본다. 항목별로 따로 읽는다.

| FN 의 지배적 단계 | 뜻 | 다음 걸음 |
| --- | --- | --- |
| `context_not_observed` 가 과반 | 참가자격 문구를 **못 찾았다**. 문서에 있는데 못 본 것 | 프롬프트가 무엇을 찾으라고 하는지 고친다. 문서 길이 확대는 **먼저 시도하지 않는다** |
| `condition_not_met` 이 과반 | 문구는 **봤는데** 금액 구간·기업 범위를 잘못 맞췄다 | 조건표(v14 ≥2.3억 / v15 1억~2.3억)를 프롬프트에 넣는 후보. 구간 게이트가 아니다 |
| `fact_not_extracted` 가 과반 | 문구는 봤고 사실을 못 뽑았다 | 출력 형식 문제일 수 있다. 회차 ② 와 묶어 본다 |
| 뚜렷한 과반이 없다 | 원인이 하나가 아니다 | **단일 처방을 만들지 않는다.** 공고별로 나눠 본다 |

앞 회차가 이 구분이 실재함을 보인다 — 같은 회차에서 v16 의 FN 5건은 전부
`context_not_observed`, v18 은 전부 `condition_not_met` 이었다(`colab-1789695980726180378`).
**같은 처방을 두 항목에 쓰면 안 되는 사례가 이미 있다.**

### 양성 판정 수로 무엇을 결론하나

| 관측 | 결론 |
| --- | --- |
| TP > 0 | **이 회차의 성과다.** 제출 파이프라인은 v14·v15·v17 에서 FN 8·6·3 이다 |
| TP = 0 이고 양성 판정도 0 | 모델이 이 항목을 아예 안 켠다. 항목 정의 전달이 문제다 |
| TP = 0 인데 양성 판정이 많다 | 켜지긴 하는데 엉뚱한 공고다. 적용 구간 전달이 문제다 |

### 구간 오버레이로 무엇을 결론하나

`+ 조건표 구간 덧씌움` 줄이다. **이것은 채택 판단이 아니다.**

- **구간이 TP 를 하나라도 지우면 조건표가 조문과 어긋난 것이다.** 스크립트가
  `!! 구간이 지운 TP` 로 띄운다. 그러면 구간을 고치는 것이 아니라 **조문을 다시 읽는다.**
- FP 만 줄면 조건표가 라벨과 어긋나지 않는다는 뜻이다. **FN 은 그대로다** — 구간은
  양성을 지우는 방향으로만 작동하므로 FN 8·6 을 고치지 못한다. 이미 확정된 사실이다.

### 근거 없는 양성으로 무엇을 결론하나

`근거 없는 양성(인용 null + 판정 1)` 줄이다. v14·v15·v17 은 **부재탐지가 아니라** 제한이
있는 것이 위반이므로 그 문구를 인용할 수 있어야 하고 제출 e 열도 채워야 한다.

**v17 에는 비교할 기준이 이미 있다.** 제출 파이프라인의 v17 양성 중 근거 빈칸이
6개 회차 전부에서 9~10건이고 **그 안에 TP 가 하나도 없다**([C1 5절](../c1-v17/README.md#5-근거-빈칸-양성--v17-에-한해-tp-가-0-이다)).
별도 질의에서 이 비율이 낮아지면 인용을 못 받아 낸 것이 프롬프트 탓이라는 뜻이다.

| 비율 | 결론 |
| --- | --- |
| 낮다 | 판정과 근거가 함께 간다. 그대로 후보로 옮길 수 있다 |
| 높다 | **TP 가 나와도 그대로 쓸 수 없다.** 제출에 넣으면 e 열이 비어 `validate_csv` 가 막거나 근거 없는 양성이 된다 |

**그중 정답도 양성인 건**을 따로 센다. 그 건들은 "맞혔지만 근거를 못 댄" 것이라
프롬프트가 인용을 요구하는 방식의 문제이지 판정의 문제가 아니다.

### 쓰지 않을 것

- **`판정` 과 `막힌_단계` 가 어긋난 줄.** 스크립트가 건수를 경고로 띄운다.
  새 회차는 `판정` 이 파생이라 0 이어야 한다. **0 이 아니면 그 회차의 단계 히스토그램을
  근거로 쓰지 않는다.**
- **전체 Macro F1.** 이 회차는 제출 CSV 를 만들지 않는다.
- **다른 회차의 수치와 직접 비교.** 별도 질의의 양성 총수가 회차마다 370/600 과 66/600 로
  갈렸다. 회차 이름 없이 인용하지 않는다.

## 7. 증거 수준

지금까지는 **CPU 준비만이다.** mock 실행·스크립트 검증·조건표는 전부 모델을 부르지 않았다.
이 회차가 돌면 **실제 GPU 회차**가 되며, 그것도 대회 서버 성공과는 다른 사건이다.
