`script.py` 의 후처리를 바꾸면 그 고정값이 당연히 어긋난다. 회차용 커밋을 `feat/c-v11`

## 3. 두 회차 설계 — 대조군은 안 돌린다

### 3-1. 무엇을 두 번 돌리나

같은 ZIP · 같은 `REPO_REF` 로 두 번. 새 작업 폴더에서 시작하고 두 결과 ZIP 을 다 보관한다
(`docs/colab.md` §"항목 진단 전용 회차").

| | `REPO_REF` | 목적 |
| --- | --- | --- |
| 1회차 | `d8dd6076fecbc860a75b8621b0df7f2a63aaaad5` | (a)(b)(d) |
| 2회차 | 같은 `d8dd6076fecbc860a75b8621b0df7f2a63aaaad5` | (c) churn — 한 회차로는 못 잰다 |

### 3-2. 대조 회차(후보 없는 코드)는 안 돌린다

이 후보는 후처리다. 그래서 같은 회차의 원응답을 재생하면 기준과 후보를 같은 모델
출력 위에서 비교할 수 있다.

```
회차가 남긴 dev-debug/diagnostics.jsonl
   ├─ 기준 코드로 재생   → 기준 CSV     (--script <기준 커밋>:script.py)
   └─ 후보 코드로 재생   → 후보 CSV     (--script <회차 커밋>:script.py)
```

대조 회차를 따로 돌리면 오히려 나빠진다 — 두 회차의 모델 출력이 달라 churn 과 후보
효과가 섞인다. 같은 원응답 위에서 비교해야 후보의 효과만 분리된다.

이것은 재생 후보의 성질이고 W5 가 "재생 후보는 두 번째 회차가 없다" 고 적은 것과 같은
이유다. 다만 여기서 두 회차를 도는 것은 후보를 재는 것이 아니라 churn 을 재기 위해서다.
두 목적을 섞지 않는다.

> 프롬프트·스키마를 바꾸는 후보였다면 대조 회차가 필요했다. 이 후보는 아니다 — §1-1 이
> 프롬프트·스키마·추가 호출이 전부 불변임을 적는다.

### 4-0. 두 함정 — 리뷰 [P2] 가 잡은 것

① 대상 밖 승인 규칙이 틀렸었다. 첫 판의 기준 D 는 `대상 밖 바뀐 셀이 churn 범위
(17~45셀) 안` 이었다. **서로 다른 두 비교를 한 칸에 넣은 것이다.**

| 비교 | 무엇이 다르나 | 대상 밖 허용 |
| --- | --- | --- |
| 같은 원응답 위 기준↔후보 | 코드만 다르다. 결정적이다 | 정확히 0 — 후보는 `v11` 키 하나만 쓴다 |
| 회차1↔회차2 | 모델 출력이 다르다 | 17~45셀 (과거 실측) |

첫 판대로면 기준↔후보에서 대상 밖 45셀이 바뀌어도 통과한다. 그건 후보가 v11 밖을
건드렸다는 뜻이고 즉시 반려해야 할 신호다. CPU 재생에서 그 값은 0셀이었다
(`CANDIDATE.md` §0). D1 과 D2 로 갈랐다.

② 후보가 아무것도 안 해도 통과했다. 첫 판의 A~E 는 전부 절대값이라, 후보가
새 출력에서 한 셀도 못 움직이면 이렇게 된다.

| 기준 | 무효과일 때 (기준 v11 = 2/3/4) | 통과? |
| --- | --- | --- |
| A (4 ≤ TP ≤ 6) | TP 2 | 실패 |
| B (FP ≤ 6) | FP 3 | 통과 |
| C (다른 항목 TP 손실 0) | 손실 0 | 통과 |
| D (대상 밖 churn 범위) | 0셀 | 통과 |
| E (발화 3~12) | 발화는 참인데 셀이 이미 1 이면 안 움직인다 | 통과 가능 |

A 하나만 걸리는 설계였다. 그리고 A 도 "재생값 근처" 라는 절대 구간이라, 기준선이
움직이면 같이 흔들린다. 기준 Z 를 앞에 세워 "후보가 움직였는가" 를 먼저 묻는다.

Z 가 실패하면 나머지를 보지 않는다. `.wiki/gpu-before-review` 가 정한 그대로다 —
"발동이 확인됐는데 대상 셀·TP/FP/FN 이 그대로면 가설 기각이다."

### 4-1. 각 기준의 정의

Z — 무엇을 "움직였다" 로 보나. 같은 회차의 원응답 위에서 기준 코드와 후보 코드를
각각 재생해(§5-2) 그 차이를 본다. v11 FN 이 최소 하나 줄고 바뀐 셀이 하나 이상이어야
한다. 둘 중 하나라도 0 이면 가설 기각이고 A~E 를 보지 않는다.

> 왜 FN 인가. 이 후보가 하는 일은 "부재를 관측했는데 게이트가 안 열려 놓친 것" 을
> 여는 것이다. FN 이 안 줄면 그 자리를 하나도 못 열었다는 뜻이고, TP·FP 가 우연히
> 좋게 나와도 후보가 한 일이 아니다.

A — TP 4~6. v11 의 dev 라벨 양성이 6건이다. 한 건이 F1 을 0.08 넘게 움직이는
규모라 ±1 보다 좁게 잡을 수 없다. TP ≤ 3 이면 재생이 과대였다는 뜻이고 후보를 보류한다.

B — FP ≤ 6 초과 시. 재생 6 을 넘으면 초과분을 공고 단위로 연다.

| 초과 | 판정 |
| --- | --- |
| 7~8 | churn 범위 안일 수 있다. 두 회차의 FP 공고 집합을 비교해 겹치지 않는 것이 몇 건인지 센다. 겹치는 핵심이 6건이면 보류가 아니라 churn 으로 적는다 |
| 9 이상 | 보류. 재생이 낙관적이었다는 뜻이다. `CANDIDATE.md` §10 이 적은 "v10 의 오탐을 v11 로 옮긴다" 가 새 출력에서 더 크게 나온 것으로 읽는다 |

D1 — 정확히 0 이다. 범위가 아니다. 같은 원응답 위에서 코드만 바뀌므로 결과는
결정적이다. 후보는 `out["v11"]` 하나만 쓰고 다른 23항목을 안 건드린다(검사로 고정).
대상 밖이 1셀이라도 움직이면 후보가 설계대로 동작하지 않은 것이고 즉시 반려한다 —
churn 으로 설명하지 않는다. churn 은 다른 출력 사이에서만 쓰는 말이다.

D2 — 판정이 아니라 기록이다. 회차1↔회차2 의 차이는 이 후보의 효과가 아니라 모델
출력의 흔들림이다. 17~45셀은 과거 코드의 13쌍에서 온 참고값이고 현재 코드의 허용선이
아니다. 이 회차가 현재 코드의 churn 을 처음 잰다((c)).

E — "크게 갈린다". 발화 조건 참이 3 미만 또는 12 초과면 (a) 가 부정된 것으로 적는다.
재생 6 의 절반·두 배다. 이 후보는 모델의 부재 관측에 걸려 있어 그 관측 자체가 회차마다
흔들리면 후보의 전제가 무너진다.

> E 가 참이어도 Z 가 거짓일 수 있다. 발화 조건이 참인데 그 공고의 v11 이 앞 단계에서
> 이미 1 이면 셀이 안 움직인다. dev 재생에서는 겹침이 0 이었지만(6건 대 6셀) 새 출력에서
> 같다는 보장이 없다. 그래서 발화 수와 변경 셀 수를 따로 센다.

## 5. 결과 감사 절차 — 명령 그대로

### 5-0. 경로 규약 — 두 종류를 섞지 않는다

| 쓰는 말 | 무엇 |
| --- | --- |
| `<inbox>` | 받은 결과 ZIP 을 푼 곳 |
| `<run1>` · `<run2>` | 등록 뒤 `reports/runs/<run-id>/` |
| `<pin>` | `git show <커밋>:script.py` 로 꺼낸 임시 파일 |

등록된 회차의 CSV 는 루트가 아니라 `<run>/dev-debug/submission.csv` 다.

### 5-1. 등록과 바이트 재현

```bash
# 1) 등록 — 회차마다 한 번
py -X utf8 tools/register_run.py --inbox <inbox> --code-commit d8dd6076fecbc860a75b8621b0df7f2a63aaaad5

# 2) 회차 CSV 를 그 코드로 재생해 바이트가 같은지 본다
git show d8dd6076fecbc860a75b8621b0df7f2a63aaaad5:script.py > <pin>/run.py
py -X utf8 tools/replay_run.py --case <run1>/dev-debug --script <pin>/run.py \
  --output-dir <tmp>/verify1 --verify
```

`--verify` 가 통과해야 그 회차의 CSV 를 근거로 쓸 수 있다.

### 5-2. 기준 대 후보 — 같은 원응답 위에서 (기준 Z · A · B · C · D1)

```bash
git show 36628dea722d4deb2529e466554473454081d11a:script.py > <pin>/base.py     # 후보가 없는 코드
git show d8dd6076fecbc860a75b8621b0df7f2a63aaaad5:script.py  > <pin>/run.py      # 후보가 있는 코드

py -X utf8 tools/replay_run.py --case <run1>/dev-debug --script <pin>/base.py \
  --output-dir <tmp>/r1-base
py -X utf8 tools/replay_run.py --case <run1>/dev-debug --script <pin>/run.py \
  --output-dir <tmp>/r1-cand

py -X utf8 tools/compare_runs.py --before <tmp>/r1-base/submission.csv \
  --after <tmp>/r1-cand/submission.csv --truth open/dev_labels.csv \
  --items v11 --output-dir <tmp>/r1-cmp
```

2회차도 같게 돌린다(`<run2>`, `r2-*`).

이 대조 하나가 Z·A·B·C·D1 을 다 답한다. `comparison.json` 에서 이렇게 읽는다.

`--items` 는 `v11` 하나다. 넷을 다 대상으로 잡으면 v10·v12·v13 이 대상 안이 되어
`changed_cells_off_focus` 가 그 셋의 회귀를 못 본다. `v11` 만 대상으로 두면 나머지
23항목이 전부 대상 밖이 되고, D1 이 v10·v12·v13 의 회귀까지 직접 잡는다.

두 옵션을 CPU 재생에서 실제로 돌려 확인했다 — 바뀐 셀 6 · 대상 밖 0 으로 같고,
`v10`·`v12`·`v13` 의 `after.tp`(4 · 4 · 3)는 대상 밖이어도 그대로 읽힌다. 기준 C 를
읽는 데 지장이 없고 D1 만 엄격해진다.

`items` 는 딕셔너리가 아니라 24개짜리 리스트이고 각 원소가 `item`·`before`·`after`·
`flipped` 를 든다(대상 밖 항목도 다 들어 있다). 아래 표기는 실제 파일에서 확인한 것이다.

| 기준 | 어디를 보나 |
| --- | --- |
| Z | `v11` 원소의 `before.fn > after.fn` 그리고 `changed_cells > 0` |
| A · B | `v11` 원소의 `after.tp` · `after.fp` |
| C | `v10`·`v12`·`v13` 원소의 `after.tp` 가 각각 4 · 4 · 3 이상 |
| D1 | `changed_cells_off_focus` 가 정확히 0 — `v11` 말고 23항목 전부를 덮는다 |
| 바뀐 공고 | `v11` 원소의 `flipped` (재생에서는 `039`·`040`·`061`·`062`·`064`·`12`) |

한 줄로 읽으려면 이렇게 한다.

```bash
py -X utf8 -c "import json,sys; d=json.load(open(sys.argv[1],encoding='utf-8')); v={r['item']:r for r in d['items']}; print('Z', v['v11']['before']['fn'], '->', v['v11']['after']['fn'], '· 바뀐 셀', d['changed_cells']); print('A/B', v['v11']['after']); print('C', {i: v[i]['after']['tp'] for i in ('v10','v12','v13')}); print('D1 대상 밖', d['changed_cells_off_focus'])" <tmp>/r1-cmp/comparison.json
```

`changed_cells_off_focus` 에 churn 범위를 적용하지 않는다. 여기서 다른 것은 코드뿐이다.

모든 재생 명령에 `--script` 를 박았다. 작업 트리 판을 쓰면 오늘 blob 이 같아도 내일
갈린다 — #124 의 [P2] 가 그 자리였다.

### 5-5. `dev` 와 `dev-debug` 를 같은 저울로 읽지 않는다

노트북은 dev 를 두 번 돌린다 — `[14]` 의 `dev`(제출 경로)와 `[18]` 의
`dev-debug`(원응답 보존). 둘은 다른 실행이고 같은 수가 나온다는 보장이 없다.

- 판정은 `dev-debug` 로 한다. 재생이 가능한 쪽이고, 기준·후보를 같은 출력 위에서
  비교할 수 있는 유일한 자료다.
- `dev` 의 점수는 참고로만 적는다. 두 수를 한 표에 섞지 않는다.

## 7. 증거 수준

이 회차가 만드는 것은 실제 GPU 회차다. CPU 재생 · 실제 GPU 회차 · 대회 서버는 서로
다른 사건이고 이 문서는 가운데 하나만 다룬다.

- 여기 적힌 재생값(5/6/1 등)은 CPU 재생의 실측이다. 회차 결과가 그것과 다를 수 있고,
  다른 것 자체가 (a)~(d) 의 답이다.
- 산술은 없다. §4 의 기준은 재생 실측과 `reproducibility.md` 의 과거 실측에서 왔다.
- dev 이득을 서버 이득으로 환산하지 않는다.

## 8. 미확인 사항

- 새 출력에서 발화 조건이 몇 건일지. 이 회차가 답한다((a)).
- 이 후보 기준의 churn 범위. §4 기준 D 는 과거 코드의 13쌍에서 온 것이고
  현재 코드의 것이 아니다. 이 회차가 처음 잰다((c)).
- 무라벨 0→1 167셀의 정확도. 라벨이 없어 이 회차로도 못 잰다.
- 서버 점수. 별개 사건이다.
