2. 같은 코드 **두 회차의 churn** — N3 는 추가 호출을 늘리는 모델 앞 단계 후보라
   `docs/workflow.md` W5 가 두 번째 회차를 요구한다
3. 원응답 — 나중에 후보를 재생으로 재는 자료

## 1. 왜 브랜치를 새로 만들었나

`gpu-run-queue.md` 의 N3 커밋(`2a5a38c`·`d808922`)은 **`ca352d6`(#142) 기반**이다.
그 뒤 `main` 의 `script.py` 에 **110줄이 더 들어왔다**(#149 의 v5 규칙 등).

그대로 돌리면 둘이 겹친다 — 낡은 코드로 GPU 를 태우고, 같은 날 기준 회차와 견줄 때
**N3 효과와 그 110줄 차이가 섞인다.** 한 회차에 두 변수다.

기존 브랜치는 **건드리지 않았다.** A 의 기록이므로 그대로 두고 새로 만들었다.

| | 기존 (낡음) | **이번 (r2)** |
| --- | --- | --- |
| 브랜치 | `run/a-n3-product` | **`run/a-n3-product-r2`** |
| 기반 | `ca352d6` (#142) | **`de5b873`** (현재 `main`) |
| 코드 커밋 | `2a5a38c` | **`ea1d8ad24da754a2537e8ffcb998926b09f0d9bb`** |
| 링크 커밋 | `d808922` | **`b521bb24c572e2d00ed8500edd0464cf537467a1`** |

두 커밋이 `main` 대비 바꾼 것은 **`script.py` 1줄 + 노트북 `REPO_REF` 1줄**뿐이다.

```
PRODUCT_ITEMS: List[str] = ["v10", "v11", "v12"]   # script.py:110
```

## 2. 열 링크 — 이것으로 연다

```
https://colab.research.google.com/github/LittleBitAI/ai-nara-shop/blob/b521bb24c572e2d00ed8500edd0464cf537467a1/notebooks/colab-baseline.ipynb
```

**반드시 링크 커밋(`b521bb2`)으로 연다.** 코드 커밋(`ea1d8ad`)에서 열면 그 판의
`REPO_REF` 는 `"main"` 이라 **N3 가 꺼진 `main` 을 돈다.**

열고 나서 셀 `[1]` 이 아래인지 눈으로 확인한다. 고칠 것은 없다.

```python
REPO_REF = "ea1d8ad24da754a2537e8ffcb998926b09f0d9bb"  # run/a-n3-product-r2 코드 커밋. N3 를 켠 판이다
```

`REPO_REF` 를 정의하는 셀은 `[1]` **하나뿐**이다. 노트북이 약칭 SHA 를 거부하므로
40자 전체를 박아 두었다 — 줄이지 않는다.

## 3. 실행 — 첫 셀부터, 두 번

### 3-0. Colab 셀에서 고칠 것은 없다. 확인할 것은 셋이다

`REPO_REF` 는 링크 커밋에 박혀 있어 **타이핑할 것이 없다.** 대신 아래 셋을 확인한다.

| 셀 | 무엇 | 해야 할 일 |
| --- | --- | --- |
| `[1]` | `SOURCE_MODE = "clone"` · `REPO_REF = "ea1d8ad…"` | **눈으로 확인만.** 고치지 않는다 |
| `[10]` | `HF_TOKEN` | **Colab 보안 비밀에 등록하고 노트북 접근을 허용한다.** 없으면 셀이 `getpass` 로 묻고, 비우면 `ValueError` 로 죽는다 |
| `[18]` | `RUN_DIAGNOSTIC = True` · `DIAGNOSE_ITEMS = ""` | **반드시 실행한다.** 기본값이 이미 맞다 — 아래 이유를 본다 |

**셀 `[18]` 을 건너뛰면 이 회차는 판정에 못 쓴다.** `[14]` 의 `dev` 통과는
`--debug-responses` 가 꺼져 있어 `diagnostics.jsonl` 에 `response_text` 가 안 남는다
(9/25 회차 실측: `dev` 508건 중 **0건**, `dev-debug` 504건 중 **504건**). 원응답이 없으면
기준선을 재생으로 못 만들고, 그러면 N3 효과를 뗄 수 없다.

`DIAGNOSE_ITEMS` 는 **비워 둔다.** 별도 항목 질의는 이 회차의 목적이 아니고 시간만 쓴다.

### 3-1. 누르는 순서

**첫 셀부터 순서대로** 누른다. 중간부터 누르면 앞 셀이 만든 `WORK`·`run_case()` 가 없다.

| 회차 | 무엇 | 왜 |
| --- | --- | --- |
| **1회차** | 노트북을 처음부터 끝까지 | 효과를 본다 |
| **2회차** | **런타임을 새로 잡고** 같은 링크로 처음부터 끝까지 | churn 을 잰다. 같은 코드 두 회차로만 잰다 |

두 회차의 결과 ZIP 을 **둘 다** 보관한다. 2회차를 같은 런타임에서 이어 돌리지 않는다 —
`run_case` 가 `mkdir(parents=True)` 라 같은 이름 재실행이 `FileExistsError` 다.

받은 ZIP 안에 이것이 있어야 한다.

| 경로 | 확인 |
| --- | --- |
| `dev-debug/submission.csv` | **판정은 이것으로 한다** |
| `dev-debug/diagnostics.jsonl` | `response_text` 가 200건 있는가 — 없으면 셀 `[18]` 을 안 돌린 것이다 |
| `dev-debug/run_report.json` | `settings.product_items` 가 `["v10","v11","v12"]` 인가 |
| `dev/submission.csv` | 참고용. `dev-debug` 와 한 표에 섞지 않는다 |
| `source.json` | `commit` 이 `ea1d8ad24da754a2537e8ffcb998926b09f0d9bb` 인가 |

예상 소요는 회차당 셋업 + 약 20분이다(현재 기준 dev 추론 727.7초에 추가 호출 200건이
붙는다). 정확한 수는 회차가 알려 준다.

## 4. 걸릴 수 있는 자리

| 증상 | 왜 | 어떻게 |
| --- | --- | --- |
| 샘플 10건에서 `check_live` 실패 | **이번 노트북은 해당 없다.** `colab-baseline.ipynb` 의 `check_live` 는 `extra_call_items()` 로 허용 항목을 읽는다 — `PRODUCT_ITEMS` 를 켜면 그 목록에 자동으로 들어간다(`script.py:122`) | — |
| `submit.zip` 이 안 나온다 | 품질 게이트. `macro_f1` 이 같은 회차의 기준보다 낮으면 제출 ZIP 을 안 준다 | **고장이 아니다.** 결과 ZIP 은 받아진다. 셀 `[20]` 을 따로 실행한다 |
| 중간 셀이 실패 | — | 셀 `[20]` 을 따로 실행해 로그 ZIP 을 받는다(`docs/colab.md` §8) |
| `REPO_REF` 가 `main` 으로 보인다 | 링크 커밋이 아니라 코드 커밋이나 `main` 에서 열었다 | 링크를 다시 확인한다(§2). 그대로 돌리면 N3 가 꺼진 회차다 |
| 약칭 SHA 오류 | `REPO_REF` 를 줄여 적었다 | 40자 전체를 쓴다. 노트북이 명시적으로 거부한다 |

코드와 안 맞고, 그 `check_live` 가 낡은 불변식으로 회차를 샘플 10건에서 죽인다
(`gpu-run-queue.md`).


판정은 `AUDIT.md` 의 명령을 그대로 돌린다. 그 문서는 **회차 전에 고정됐다.**

## 6. 이 회차가 답하지 않는 것

- **서버 점수.** 회차는 서버가 아니고, 그 전에 이 변경은 시간 한도를 넘는다(§0).
- **채택 여부.** A 가 정한다. 이 카드는 실행 묶음이다.
- **+0.003788 이 진짜인지.** 그 크기는 관측된 회차 변동폭(0.034)보다 작다.
  두 회차로도 그 크기를 확정하지 못한다 — §0 이 적은 그대로다.
