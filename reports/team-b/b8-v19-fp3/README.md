## 오탐 셋 — 공고별

v19 는 입찰·투찰 단계에서 확약서를 요구한 경우로 한정한다(`docs/items.md` 2026-09-18 확정 해석).
운영 코드는 `확약서` 앞뒤 200자에 `입찰서 제출 마감`·`입찰 전`·`투찰 마감`·`개찰 전`·`입찰 참가 시` 가
있으면 입찰 단계 요구로 본다.

| 공고 | 모델 인용 | 창이 집은 마감 표현의 주인 |
| --- | --- | --- |
| `PPS-DEV-096` | `정품공급 확약서 1부.` | 앞 문장 — 중소기업확인서 `전자입찰서 제출 마감일 전일까지 발급` |
| `PPS-DEV-098` | `제조사의 물품공급확약서(…) … 제출이 가능한 업체` | 앞 항목 — 시약판매업 `전자입찰서 제출 마감일 전일까지` 등록. 확약서 줄 자체는 `계약 전 제출` |
| `PPS-DEV-112` | `… 공급 증명원 및 A/S 확약서를 제출할 수 있는 업체` | 앞 항목 — `입찰서 제출 마감일 전일까지` 세부품명 입찰참가 등록 |

세 공고 모두 확약서가 적힌 줄에는 입찰 단계 시점이 없다. 미탐 둘은 이 규칙과 무관하다. 모델은 둘 다
v19=1 을 냈다. `033` 은 공고 어디에도 입찰 단계 시점이 없어 내려간다(PR #30 이 알고 잃은 정탐).
`036` 은 입찰 단계 요구가 확인되고 인용도 그 문장인데, 원문이 `마감일` 뒤에서 줄이 바뀌고 모델 인용은
공백이라 원문 대조(`clean_evidence`)에서 떨어져 근거 계약이 내린다. 밴드 인용 게이트가 쓰는
`restore_spacing()` 을 근거 대조에도 쓰면 살아날 꼴이지만, 모든 항목의 근거 경로를 바꾸는 일이라 따로 둔다.

## 후보와 측정

창을 확약서가 적힌 줄로 좁힌다. 200자 창과의 교집합이라 지금보다 넓어지지 않는다 — 줄만 쓰면 한 줄이
긴 공고에서 창이 커져 무라벨 한 칸을 새로 올렸다(`PPS-D-011943`).

dev 에서는 오탐 셋만 내려가고 정탐 넷(`23`·`034`·`035`·`037`)은 그대로다. 다른 원응답
(`colab-1789655036303880754/dev-debug`)에서도 같은 세 공고의 v19 만 내려간다.

무라벨 2,000건(`run-1790141381430477242`, 실제 응답)에서는 v19 양성 22 중 20 을 내린다.
dev 는 7 중 3(43%)이고 무라벨은 22 중 20(91%)이다. 내린 20건을 읽고 꼴을 붙였다
([`unlabeled-replay.json`](unlabeled-replay.json), 정답이 없으므로 꼴이지 판정이 아니다).

| 꼴 | 셀 |
| --- | ---: |
| 계약·착수·납품·낙찰 뒤 제출 | 7 |
| 적격심사·제안서 평가 때 제출(개찰·제출 뒤) | 5 |
| 시점 없음(`제출 가능한 업체`) | 2 |
| 목록 머리말에 입찰 단계 시점 — 입찰 단계 요구 | 3 |
| 인용이 확약서가 아니거나 머리말 미확인 | 3 |

앞의 열넷은 확정 해석대로라면 내려가는 것이 맞는 꼴이다. 거꾸로 말하면 지금 HEAD 는 무라벨 v19 양성
22 중 적어도 14 가 입찰 단계 요구가 아닌 꼴이다 — dev 오탐 셋과 같은 이유로 살아 있다.

채택을 막는 것은 머리말 셋이다.

```
PPS-D-020461  4. 제출 서류 / 가. 투찰 시 제출 (나라장터에 파일로 업로드) / ① 사업자등록증 1부 / … / ⑨ 확약서 1부
PPS-D-015754  3. 입찰 참여자는 입찰 전에 반드시 아래의 서류를 제출하여 … / ① 카탈로그와 규격서 / ② 제조사 또는 수입사의 물품공급확약서
PPS-D-003569  8. 제출서류 : … / 가. 입찰참가신청서 / … / 바. 입찰보증보험증권 / … / 사. 제조사 또는 공급자 공급 증명서/국내 공급 총판 AS 확약서 1부씩
```

제출서류 목록의 한 항목인 확약서는 시점을 목록 머리말에서 받는다. 줄 하나로 좁히면 그 머리말을 잃는다.
그리고 dev 오탐 `096` 도 목록 항목이다(`2) 입찰참가자격 확인용 서류` 아래 `- 정품공급 확약서 1부.`) — 머리말을
읽는 규칙은 `096` 을 다시 살릴 수도 있다. 추출된 본문은 들여쓰기를 잃어 목록의 깊이를 줄머리 기호로만
짐작해야 하고(`①`·`가.`·`-`·`1)` 가 섞인다), `020461` 의 `투찰 시` 는 지금 `V19_BID_DEADLINE` 에 없다.
그 규칙을 세우는 것은 이 칸의 크기를 넘는다고 보고 멈췄다.

## 판정 절차 — 2026-09-23 A 결정, 결과 반려

위 판독은 사람 라벨이 아니라 내 읽기다. 삭제형 후보의 채택 임계 `q < F/2`(#95)에 대면 v19 는 dev F1 0.615 라
임계 0.308 이고, 내 판독으로 q 는 0.15~0.30 이라 그것만으로는 반려 근거가 되지 않는다. 그래서 A 가 판정
절차를 정했다. 제출과 사람 검토 없이, 결과는 채택 또는 반려 둘 중 하나로만 낸다.

1. 게이트 — dev v19 셀 9개(HEAD 정탐 4 · 오탐 3 · 미탐 2)에 Opus 5.5 라벨러를 블라인드로 돌린다.
   오탐 셋을 전부 0 으로, 정탐 넷 중 셋 이상을 1 로 맞히지 못하면 그 자리에서 반려.
2. 게이트를 지나면 6,000건 회차에서 이 후보가 지우는 v19 셀(약 60)을 라벨링해, 실제 입찰 단계 요구가
   10 이하면 채택(98.75% Wilson 상한 0.299 < 0.308), 11 이상이면 반려.

1단계 결과: 오탐 셋을 모두 1 로 냈다. 반려다.

| 셀 | 정답 | 라벨러 | 라벨러 인용 |
| --- | ---: | ---: | --- |
| 정탐 `23`·`034`·`035`·`037` | 1 | 1 | 각 공고의 입찰 마감 시점 문장 |
| 미탐 `033`·`036` | 1 | 1 | — |
| 오탐 `096` | 0 | 1 | `다. 정품공급확약서 제출이 가능한 업체이어야 합니다.` |
| 오탐 `098` | 0 | 1 | `… 물품공급확약서(…) … 제출이 가능한 업체` |
| 오탐 `112` | 0 | 1 | `… 공급 증명원 및 A/S 확약서를 제출할 수 있는 업체` |

라벨러는 v19 에서 재현율 6/6 · 음성 0/3 이다. 틀리는 모양이 이 후보가 지우는 모양과 같다 — 시점 없는
`제출 가능한 업체` 를 입찰 단계 요구로 읽는다. 그래서 2단계의 셀을 이 라벨러로 가를 수 없고, 1단계에서
끝난다. 호출 9회·427초, 명령과 원응답 hash 는 [`labeler-gate/`](labeler-gate/).

이 반려는 "후보가 틀렸다" 는 측정이 아니라 "이 저장소가 가진 자동 수단으로는 채택 조건을 세울 수 없다" 는
뜻이다. 절차가 그 경우를 반려로 정했다.

## 다음에 연다면

- 시점을 받는 단위를 줄이 아니라 "확약서가 속한 문장 + 그 목록의 머리말" 로 정의한다. 머리말 판정은
  줄머리 기호의 종류가 바뀌는 지점으로 한다. dev `096`·무라벨 `020461`·`015754`·`003569` 를 먼저 손으로 확인한다.
- `투찰 시` 처럼 지금 패턴에 없는 입찰 단계 표현은 조문·항목표 비고(`입찰 전 발급, 계약시 제출 등 표현 다양`)
  에서 가져온다. dev 인용에서 고르지 않는다.
- 미탐 `036` 처럼 줄바꿈 때문에 원문 대조에서 떨어지는 인용이 다른 항목에 몇 셀인지 잰다
  (`postprocess` 의 근거 대조에 `restore_spacing()` 을 쓰는 후보). 전 항목에 걸리는 변경이다.
- 무라벨 v19 22건 중 열넷이 입찰 단계가 아닌 꼴이라는 관측은 이 후보와 별개로 남는다. 서버에서 v19 가
  오탐으로 기울어 있을 가능성의 신호이고 측정은 아니다.
